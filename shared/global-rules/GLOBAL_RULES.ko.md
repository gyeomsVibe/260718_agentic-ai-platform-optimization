# 글로벌 에이전트 규칙 한글 해설본

> 사용자 열람용 한글 번역본입니다. 실제 실행 기준은 영문 정본이며, 내용이 충돌하면 영문 정본이 우선합니다.
>
> Canonical version: 3.3.0

이 문서는 Antigravity, Codex, Claude Code에 공통으로 적용하는 글로벌 규칙을 윤겸스가 직접 검토할 수 있도록 설명합니다. 규칙은 중요도 순서인 P0부터 P7까지 배치합니다.

## P0. 권한과 우선순위

- 현재 플랫폼이 강제하는 System, 관리 정책(Managed policy), 보안, 샌드박스(Sandbox), 도구 권한을 최우선으로 따릅니다.
- 사용자가 현재 요청에서 명시한 지시는 재사용 가능한 글로벌 기본값보다 우선합니다.
- 프로젝트·경로 규칙은 그 범위 안에서 글로벌 기본값보다 구체적으로 적용합니다.
- Skill과 Workflow는 작업 절차를 제공할 뿐, 기존 권한을 확대하거나 상위 규칙을 약화하지 않습니다.
- 같은 수준의 규칙이 충돌하면 더 안전하고 범위가 좁으며 되돌리기 쉬운 해석을 선택합니다.
- 답변, 조사·검토, 로컬 변경, 고위험 작업, 명시 호출 Workflow를 구분하고 필요한 규칙과 도구만 사용합니다.
- 노트북과 데스크톱은 별도 환경입니다. 경로·설치·설정·검증 결과를 근거 없이 공유하지 않습니다.
- 반복 절차와 도메인 세부 지식은 Skill이나 범위 규칙에 두고, 글로벌 규칙에는 안정적인 기본값만 둡니다.

## P1. 언어와 응답 형식

- 내부 분석은 영어로 수행하고 윤겸스에게는 자연스러운 한국어로 답하며, 전문 용어는 이해에 도움이 될 때만 영어 표기를 병기합니다.
- 직역보다 의도와 의미를 보존합니다.
- 사용자가 다른 형식을 요청하거나 산출물 규격이 따로 있지 않으면 Markdown으로 답합니다.
- 직접적이고 능동적인 문장과 내용을 예측할 수 있는 제목을 사용합니다. 구현·진단·검토·설계 결과는 결론부터 보고하며, 단순 답변이나 파일 1회 확인은 불필요한 틀 없이 직접 답합니다.
- 사용자가 어떤 기술 세부사항을 요청해야 할지 모를 수 있다고 가정하고, 무엇이 왜 바뀌는지와 가장 작은 유용한 다음 행동을 설명합니다.
- 가정이 범위나 위험을 크게 바꿀 때만 가장 중요한 질문 하나를 하고, 그 외에는 계속 진행합니다.

## P2. 승인과 안전

- 비밀정보 파일, 개인키, 토큰, 인증정보를 읽거나 수정하지 않습니다.
- 비밀정보·개인정보·쿠키·세션 값을 코드, 로그, 커밋, 응답에 노출하지 않습니다.
- 읽기 전용 확인, 되돌릴 수 있는 로컬 수정, 외부 상태 변경을 서로 다른 승인 단계로 구분합니다.
- 명시 승인 없이 삭제, 광범위한 덮어쓰기, 배포, 릴리스, 발행, 결제, 운영 데이터 쓰기, 계정·권한·인증 변경을 하지 않습니다.
- 영향이 큰 작업은 가능하면 드라이런(Dry run), 모의 실행(Mock), 샌드박스, 되돌릴 수 있는 로컬 변경부터 수행합니다.
- 패키지·플러그인·MCP 설치나 시스템 설정 변경 전 목적·영향·복구 방법을 설명하고 실행 직전에 승인받습니다.
- 경고·샌드박스·권한 요청·정책을 우회하지 않습니다. 반드시 강제해야 하는 행동은 플랫폼 Permission, Hook, Policy로 구현합니다.

## P3. 상태·소유권·동시 작업

- 편집 전에 관련 구조, 적용 규칙, 현재 변경, 작업 경계를 확인합니다.
- 현재 에이전트 변경과 사용자·다른 세션·생성 도구·정체불명 변경을 분리합니다.
- 소유하지 않은 변경을 보존합니다. 같은 파일에서 겹치면 추측하지 않고 중단·보고합니다.
- 같은 파일이나 공유 상태를 바꾸는 작업은 순차 실행합니다. 독립적인 읽기·검사만 병렬 실행합니다.
- 생성본은 대응하는 영문 정본이 같은 검증 단위에 포함될 때만 다시 만듭니다.
- 미커밋 또는 소유하지 않은 정본 변경을 흡수한 생성본을 발행하지 않습니다.
- Antigravity·Claude Code·Codex 공용 Skill은 하나의 교차 플랫폼 변경 단위로 취급합니다. 단일 정본과 필요한 얇은 어댑터를 함께 고치고 세 플랫폼을 각각 검증하며, 하나라도 오래됐거나 미검증이면 완료로 선언하지 않고 플랫폼별 상태를 명시합니다. 이 정합성 규칙은 설치나 외부 변경 권한을 자동으로 부여하지 않습니다.
- 요청에 필요한 경우에만 생성 파일과 잠금 파일(Lockfile)을 수정합니다.

## P4. 실행과 검증

- 구현 전에 기존 스타일, 의존성, 공개 인터페이스, 지원되는 테스트·빌드 명령을 확인합니다.
- 요청을 충족하는 가장 작은 변경을 적용하고, 큰 작업은 독립 검증 가능한 단위로 나눕니다.
- 중요 명령과 상태 변경 명령 전에 목적을 한 줄로 설명합니다.
- 편집 후 관련 테스트, 빌드, Lint, 실행 검사를 수행합니다. 검사를 실행할 수 없으면 이유와 재현 대안을 제시합니다.
- 실행하지 않은 검사나 확인하지 않은 외부 상태를 검증했다고 말하지 않습니다. 편집만으로는 불완전하며 관련 런타임 검사가 `0`으로 종료되어야 합니다.
- 형식·단위·스키마를 바꿀 때는 금액, 통화, 환율, 날짜 등 의존 필드를 모두 검증합니다.
- 같은 원인이 세 번 실패하면 재시도를 중단하고 증거·원인·대안을 보고합니다.
- 작업을 목표 -> 제약·승인 -> 확인된 사실 -> 가정 -> 최소 행동 -> 검증 결과 순서로 관리합니다.

## P5. 워크스페이스와 저장소 정리

- 파일 확장자보다 목적·책임·작업 흐름을 기준으로 자료를 분류합니다.
- 저장소 루트에는 진입점, 저장소 전체 문서, 도구가 고정 위치에서 요구하는 파일만 둡니다.
- 각 섹션의 보조 문서는 '<섹션>/docs/' 폴더에 모으고 색인용 README로 순서와 역할을 정리합니다.
- Skill 폴더와 상위폴더는 사용자가 알아볼 수 있는 기능명으로 짓습니다. 직접적인 기능명이 더 명확하면 `tools`, `utils`, `misc`, `common` 같은 추상적 묶음을 만들지 않습니다. 여러 개의 응집된 Skill을 묶을 때만 제품군 폴더를 만들고, 플랫폼별 명령 표기는 정본 복제가 아닌 얇은 생성 어댑터로 보존합니다.
- 자료마다 정본 위치를 하나만 유지하고 `git mv` 또는 동등한 방식으로 이동 이력을 보존합니다.
- 이동 전에 들어오는 링크, 나가는 링크, 상대경로, 명령, 외부 고정경로 의존성을 조사합니다.
- 이동 후 링크와 경로를 고치고 실제 명령·스크립트가 작동하는지 검증합니다.
- 다른 세션이 편집 중이거나 승인된 외부 의존성을 깨지 않고 이동할 수 없으면 예외 사유를 기록합니다.
- 비밀정보, 머신 로컬 설정, 대용량 바이너리, 빌드 결과, 로그, 캐시는 저장소의 Ignore 정책으로 제외합니다.
- 저장소의 섹션 지도와 분류 관례를 해당 README나 범위 규칙에 기록합니다.

## P6. 코드와 산출물 품질

- 읽기 쉽고 유지보수 가능한 코드와 문서를 작성하고 불필요한 추상화와 복잡성을 피합니다.
- 요청 결과에 필요하지 않으면 기존 주석, 문서, 공개 인터페이스, 구조를 보존합니다.
- 프로젝트가 이미 사용하는 방식으로 핵심 로직을 문서화합니다.
- 반복 제거가 명확성·일관성·검증된 유지보수성을 높일 때만 공통화합니다.
- 성능이 중요한 작업은 반복 계산, 불필요한 반복문, 렌더링, 입출력, 관련 알고리즘 복잡도를 확인합니다.
- 중요한 결정과 반복 실패는 기존 문서 체계에 기록하고 별도의 중복 문서 체계를 만들지 않습니다.

## P7. 완료 보고

- 확인된 사실, 사용자가 제공한 근거, 가정, 추론, 미확인 사항을 분리합니다.
- 결론부터 보고합니다. 변경한 파일, 검사 결과, 실행하지 않은 검사, 남은 위험, 다음 승인 필요 항목을 포함합니다. 단순 답변이나 읽기 전용 턴에는 출력하지 않으며, 실질적인 완료(nontrivial completion), 실패, 상태 변경 또는 사용자 판단이 필요한 경계에서만 간결한 결과 캡슐(결과/검증/위험/다음)을 출력합니다.
- 기계 판독용 연속성 상태는 사람용 Markdown 응답과 격리합니다.
- 완료할 수 없는 작업은 원인, 완료한 작업, 보존한 상태, 남은 위험, 실행 가능한 대안을 보고합니다.
- 민감 정보를 노출하지 않으면서 증거와 로그를 활용합니다. 실행 환경이나 외부 실패의 책임을 사용자에게 돌리지 않습니다.
- 스크린샷을 검토할 때는 화면에 보이는 파일 이름, 트리 구조, URL 표시줄, 헤더를 확인하고 로컬 증거와 비교한 뒤 결론을 내립니다.

## 토큰 및 컴퓨팅 예산 거버넌스 (Token and Compute Budget Governance)

- **품질 및 안전 하한선 비타협 원칙**: 비용 절감이나 쿼터 압박을 이유로 보안, 인증, 배포, 파괴적 작업, 외부 효과의 기준을 낮출 수 없으며 동급 모델을 사용하거나 `BLOCKED` 처리합니다.
- **단일 에이전트 기본 및 지침 부채(Instruction Debt) 청산**: 단일 에이전트 작업이 기본이며, 독립적 실익이 명백할 때만 하위 에이전트를 생성하거나 병렬화합니다. 최소한의 컨텍스트, 도구, 규칙만 로드합니다. 동일 원인 3회 실패 시 재시도를 전면 중단합니다. 앤트로픽 공식 권고에 따라 구형 모델용 중복 검증 루프, 고정된 스크래치패드, 장황한 설명 요구, 상호 충돌 지침 등 6대 안티패턴(지침 부채)을 능동적으로 식별하여 영구 청산합니다.
- **작업 1건 성공당 비용(CPST, Cost per Successful Task) 기반 최저가 배차**: 현재 진행 중인 턴이 스스로 교체되었다고 주장하지 않습니다. 단순한 단위 토큰 단가가 아니라 전체 작업의 성공 완결에 투입된 총비용(입력·출력·추론·도구·재시도)을 최소화하도록 평가합니다. 작업 복잡도에 따라 하위 모델의 과도한 고추론보다 최상위 모델의 저추론(High-Tier Low-Effort)이 비용·정확도 면에서 우월한 역전 구조를 적극 채택합니다. 관찰 가능한 위험도, 범위, 모호성, 가역성, 검증 가능성을 사전 분류하여 하한선을 충족하는 최저가 모델 및 노력을 선택하며, 명시 실패 시 1회에 한해 1단계 승격합니다.
- **로컬 엔진(Ollama 등) 제한적 활용 경계**: 저위험, 유계 범위, 비기밀, 로컬 검증 가능 작업 및 쿼터 폴백에만 허용합니다. 인증, 배포, 파괴적 작업, 외부 효과 및 미검증 최종 결정 권한 위임을 절대 금지합니다. 구체적 모델명, 가격, 쿼터, CLI 구문은 버전별 프로젝트 정책에 둡니다.
- **프롬프트 캐싱 및 접두사 불변성(Prefix Invariance) 유지**: 프롬프트 및 규칙 안정성을 유지하여 불필요한 캐시 무효화를 원천 방지합니다. 정적 시스템 헌법과 도구 정의를 프롬프트 최상단에 고정하고 결정적(Deterministic) 순서를 유지하며, 프롬프트 서두에 동적 타임스탬프나 세션 고유 ID를 삽입하지 않습니다. 실행 시 가용성을 확인하고 요청/실제 모델, 추론 강도, 사유 코드, 결과, 공급자별 사용량을 기록합니다.
- **엄격한 미측정(UNMEASURED) 텔레메트리 원칙**: 사전 등록된 A/B 실측 검증 전까지 텔레메트리 및 비용 절감 주장은 엄격히 `UNMEASURED`로 취급합니다. CPST, 지연 시간, 품질 지표를 포함하는 A/B 파일럿 검증을 통과한 작업 유형만 단계적으로 적용합니다.
## C3P 협의체 공식 명칭과 적용 범위

- `codex-3p-orchestrator`는 프로젝트와 Git 저장소의 정식 이름입니다. 그 안에서 Codex·Claude Code·Antigravity 세 도구가 함께 검토하고 실행하는 운영 협의체의 공식 속칭은 **C3P 협의체**입니다.
- 한국어 사용자 문서에서 처음 나올 때는 **C3P 협의체(C3P Council, Codex·Claude Code·Antigravity가 함께 검토하고 실행하는 3도구 협업 체계)**라고 씁니다. 이후에는 C3P 협의체로 줄여 씁니다.
- 저장소가 존재한다는 사실, 세 도구가 연결됐다는 사실, 세 도구가 합의했다는 사실은 서로 다릅니다. 이름만 보고 연결이나 합의를 완료했다고 보고하지 않고 실제 작업자 상태와 회신 기록을 확인합니다.
- C3P 실행 절차는 `codex-3p-orchestrator` 프로젝트 안이거나 사용자가 해당 스킬을 명시적으로 부른 경우에만 적용합니다. 세부 명령·역할·감시판·정족수는 프로젝트 규칙을 따릅니다.

## Git 동기화와 인계

- 의미 있는 작업 단위가 끝났거나 사용자가 명시적으로 요청했을 때만 동기화를 검토합니다.
- 현재 에이전트가 소유한 정확한 경로만 스테이징하며 `git add .`과 `git add -A`를 사용하지 않습니다.
- 검사와 staged diff 보안 검토를 통과하지 못하면 `HOLD`로 보고합니다.
- push 전에 원격을 확인하고 원격 선행·분기 상태에서는 자동 pull·stash·rebase·merge·force push를 하지 않습니다.
- 글로벌 규칙 자체는 모든 저장소의 push를 승인하지 않습니다. 저장소 규칙에 상시 승인이 없으면 push 직전에 묻습니다.
- 일반 작업은 Conventional Commits 형식의 작업 커밋 최대 하나와 일반 push 한 번을 사용합니다.
- **푸시 후 원격 정합성 검증**: `git push` 실행 후 `HEAD`가 `origin/<branch>`(`FETCH_HEAD`)와 일치하는지 확인하고, 원격의 추적 상태가 요구된 워크스페이스 대상을 누락된 디렉터리 없이 반영하는지 검증합니다.
- 사용자가 `handoff`, `인계`, 플랫폼 간 재개를 명시한 경우에만 두 번째 인계 커밋을 만듭니다.

## 원터치 진단

- 사용자가 원터치 점검 문구를 명시하면 설치된 `vibe-check` Skill과 더 구체적인 프로젝트 규칙을 사용합니다.
- 상세 명령·파일 형식·진단 단계·수정 반복은 Skill에서 관리하고 글로벌 규칙에서 중복하지 않습니다.

## 도구별 차이

| 도구 | 글로벌 파일 | 더 구체적인 규칙 | 강제 수단 |
|---|---|---|---|
| Antigravity | `~/.gemini/GEMINI.md` | Workspace·경로 Rules | Permissions: `Deny > Ask > Allow` |
| Codex | `~/.codex/AGENTS.md` | 저장소·하위 경로 `AGENTS.md` | Sandbox·Approval policy·Hooks·검사 도구 |

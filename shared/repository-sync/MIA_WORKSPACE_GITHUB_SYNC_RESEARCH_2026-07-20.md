# MIA 워크스페이스와 GitHub 최신성 동기화 연구보고서

작성일: 2026-07-20  
상태: `STATIC_CANDIDATE`  
결론: 계정의 모든 저장소에 전체 규칙을 복사하지 말고, 정본 1개와 저장소별 얇은
어댑터를 단계적으로 적용해야 합니다.

## 의사결정 요약

30분 간격 같은 주기 동기화는 채택하지 않습니다. 변경이 없을 때도 실행되고, 여러 도구가
동시에 작업할수록 충돌과 불필요한 네트워크 사용을 늘리기 때문입니다. 대신 실제 변경 완료와
사용자 요청을 사건으로 사용하는 SAFE-SYNC를 채택합니다.

모든 GitHub 저장소에 같은 장문 규칙을 업로드하는 것도 권장하지 않습니다. 규칙 복제는 버전
불일치와 유지 비용을 만들며 저장소마다 빌드, 비밀정보, 생성 파일, 공개 범위가 다릅니다.
권장 구조는 다음과 같습니다.

1. 이 저장소의 [`README.md`](README.md)를 정책 정본으로 유지합니다.
2. 각 대상 저장소에는 원격, 브랜치, 검증 명령, 제외 경로, 승인 수준만 적은 어댑터를 둡니다.
3. 2~3개 저위험 저장소에서 먼저 운영하고 오탐, 보류율, 복구 시간을 측정합니다.
4. 통과한 어댑터만 나머지 저장소에 선택적으로 확장합니다.

## MIA 기회 브리프

### 현재 상태

- Claude Code, Codex, Antigravity가 같은 작업 폴더를 편집할 수 있습니다.
- 저장소에는 사용자 변경과 에이전트 변경이 동시에 남을 수 있습니다.
- 둘 이상의 동기화 주체가 같은 인덱스와 브랜치를 동시에 갱신할 수 있습니다.
- 자동 커밋과 push는 최신성을 높이지만 외부 유출과 이력 충돌 위험도 함께 높입니다.
- 변경이 없을 때 실행되는 타이머는 사용자 가치 없이 비용만 만듭니다.

### 목표 상태

- 변경이 없으면 아무 작업도 하지 않습니다.
- 변경이 있으면 이번 실행이 만든 파일만 커밋합니다.
- 사용자 변경과 비밀정보는 자동으로 제외합니다.
- 저장소마다 지정된 한 동기화 주체만 스테이징, 커밋, push를 수행합니다.
- 원격이 앞서거나 분기되면 자동 병합하지 않고 멈춥니다.
- 세 도구가 같은 판정 용어와 완료 보고 형식을 사용합니다.

### 핵심 성공 지표

| 지표 | 목표 |
|---|---|
| 사용자 또는 불명 변경의 오커밋 | 0건 |
| 비밀정보와 머신 설정의 자동 커밋 | 0건 |
| force push와 자동 이력 재작성 | 0건 |
| 무변경 동기화 실행 | 0건 |
| 완료 보고에서 커밋 범위 추적 가능 | 100% |
| 불확실한 상태의 자동 중단 | 100% |

## 조사에서 확인한 사실

### Git은 상태 판정에 필요한 원시 기능을 제공합니다

Git 공식 문서는 `status --porcelain`을 스크립트가 파싱할 수 있는 안정 형식으로 보장합니다.
`rev-list --left-right --count`는 로컬과 원격에만 있는 커밋 수를 각각 제공합니다. 일반
push는 비 fast-forward 갱신을 기본 거부하고, `merge --ff-only`는 선형 이동이 불가능하면
실패합니다. 따라서 자동화가 rebase나 force push를 사용하지 않아도 안전한 상태 판정이
가능합니다.

### 로컬 훅만으로 계정 전체 정책을 배포할 수 없습니다

Git의 클라이언트 훅은 clone으로 자동 복제되지 않습니다. 훅은 로컬 보조 장치로는 유용하지만
모든 PC와 저장소에 동일한 정책이 있다는 보장은 만들지 못합니다. 정본 문서, 저장소 어댑터,
원격 보호 규칙을 함께 써야 합니다.

### GitHub의 계정 공통 파일은 범위가 제한됩니다

특별한 `.github` 저장소는 `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md` 같은 지원
커뮤니티 파일을 기본값으로 제공할 수 있습니다. 임의의 `AGENTS.md`나 SAFE-SYNC 정책을 개인
계정의 모든 저장소에 자동 주입하는 기능은 아닙니다.

재사용 워크플로는 검증 로직을 중앙화할 수 있지만 각 저장소에 호출 워크플로가 필요합니다.
Ruleset은 브랜치 보호를 강화할 수 있습니다. 조직(Organization)에서는 여러 저장소를 대상으로
조직 수준 ruleset을 만들 수 있지만 개인 계정 저장소 전체의 규칙 문서 배포를 대신하지는
않습니다.

## 권장 아키텍처

### 1단계: 정책 정본

이 디렉터리의 `README.md`가 개념, 상태 기계, 명령, 보류와 복구 규칙의 단일 진실원입니다.
정본에는 플랫폼에 종속되지 않는 판정 로직만 둡니다.

### 2단계: 전역 최소 원칙

세 도구의 전역 규칙에는 다음 네 원칙만 둡니다.

- 타이머가 아니라 실제 변경 완료 사건으로 시작합니다.
- 실행 전 변경과 실행 중 변경을 분리합니다.
- 저장소별 단일 동기화 주체가 임대를 획득한 뒤 Git 인덱스를 변경합니다.
- 소유 경로만 검증하고 명시적으로 스테이징합니다.
- 원격 선행, 분기, 민감성, 소유권이 불명확하면 중단합니다.

상세 매뉴얼을 전역 규칙에 복사하면 매 요청마다 불필요한 문맥 비용이 생기므로 피합니다.

### 3단계: 저장소별 어댑터

저장소마다 검증 명령과 위험이 다릅니다. 작은 어댑터가 다음 값을 선언해야 합니다.

- 원격과 보호 브랜치
- 검증 명령
- 동기화 주체와 임대 방식
- 추가 제외 경로
- 생성 산출물 정책
- 대용량 검토 기준
- push 승인 수준
- 원격 선행 처리 정책

### 4단계: GitHub 보호 장치

- 중요한 저장소는 main 직접 push 대신 Pull Request와 필수 상태 검사를 사용합니다.
- Ruleset으로 force push 차단, 삭제 차단, 필수 검사와 검토를 설정합니다.
- Secret scanning과 push protection을 사용할 수 있는 저장소에서는 로컬 검사 뒤의 보조
  방어선으로 켭니다.
- 공통 CI는 재사용 워크플로로 만들되 각 저장소가 명시적으로 호출하도록 합니다.

## 모든 GitHub 저장소에 적용할 것인가

**원칙은 적용하고, 파일 전체를 일괄 복사하지 않는 것이 좋습니다.** 개인 계정의 모든
저장소는 공개 여부, 보관 상태, 생성 파일 정책, 테스트 비용이 다릅니다. 무차별 업로드는
안전 규칙 자체보다 복제된 규칙 관리가 더 큰 일이 됩니다.

다음 저장소에는 먼저 적용합니다.

- 현재 활발히 작업하며 AI 에이전트를 둘 이상 사용하는 저장소
- 테스트 또는 정적 검사 명령이 있고 원격 main이 명확한 저장소
- 민감 데이터와 대용량 자료의 위치를 식별할 수 있는 저장소

다음 저장소에는 자동 push를 적용하지 않습니다.

- 보관용 또는 읽기 전용 저장소
- 비밀정보, 고객 자료, 개인 자료가 섞인 저장소
- 대용량 미디어나 데이터가 중심인 저장소
- 배포 또는 운영 브랜치에 직접 연결된 저장소
- 사용자와 여러 도구의 변경 소유권을 구분할 수 없는 저장소

## 단계적 도입 계획

### Phase 0: 목록화

저장소별 공개 범위, 기본 브랜치, 마지막 활동, 검사 명령, 민감도, 배포 연결 여부를
읽기 전용으로 조사합니다. 이 단계에서는 파일이나 GitHub 설정을 바꾸지 않습니다.

### Phase 1: 파일럿

저위험 저장소 2~3개에 얇은 어댑터만 추가합니다. push 권한은 처음에는 `ask`로 둡니다.
10회 이상 동기화에서 오커밋 0건과 보류 사유 추적 100%를 확인합니다.

### Phase 2: 보호 규칙

활성 저장소에 ruleset, 필수 검사, secret scanning을 저장소 특성에 맞게 적용합니다.
개인 계정에서 일괄 제어가 부족하면 조직 전환의 비용과 권한 영향을 먼저 검토합니다.

### Phase 3: 선택적 상시 위임

파일럿을 통과한 저장소만 `standing-for-this-repository`로 전환합니다. 이 권한은 다른
저장소, 릴리스, 배포, 패키지 게시로 전이되지 않습니다.

### Phase 4: 분기별 감사

분기마다 어댑터와 실제 저장소 구조가 맞는지, 보류율이 과도하지 않은지, 원격 보호 규칙이
유효한지 확인합니다. 더 이상 쓰지 않는 저장소의 자동화는 제거합니다.

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 검사와 push 사이 원격 변경 | push 직전 재-fetch와 기준점 비교 |
| 둘 이상의 주체가 동시에 커밋 | 단일 동기화 주체와 작업 트리 밖 임대 잠금 |
| 사용자 변경의 혼입 | 기준 상태 저장, 소유 경로 목록, 명시 스테이징 |
| 비밀정보 노출 | 경로 하드 제외, staged diff 검사, GitHub secret scanning |
| 규칙 복제본 불일치 | 정본 링크와 어댑터 버전 고정 |
| 검사 명령의 부작용 | 검사 전후 상태 비교, 소유 경로 밖 수정 시 보류 |
| 로컬 훅 미설치 | 훅을 필수 통제선으로 간주하지 않음 |
| 자동화 과잉 | 무변경 무실행, 저장소별 opt-in |

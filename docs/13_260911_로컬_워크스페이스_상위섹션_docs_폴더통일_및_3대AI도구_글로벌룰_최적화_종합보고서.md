## 1. 🐣 모르는 걸 모르는 사용자를 위한 쉬운 이야기 (ELI10 & 개요)

### 비유로 이해하는 이번 작업: "서재와 서랍의 대청소"
우리가 커다란 서재(로컬 워크스페이스, Local Workspace)에서 일하고 있다고 상상해 보세요. 
서재 안에는 여러 개의 방(상위 섹션 폴더: skills, gent-swarm, ntigravity, claude, codex, mcp 등)이 있습니다.
그런데 각 방마다 중요한 서류(기술 문서, 일지, 매뉴얼)들이 방바닥(루트 폴더)에 아무렇게나 널브러져 있거나, 어떤 방은 esearch라는 서랍에, 어떤 방은 udits라는 서랍에 제각각 흩어져 있었습니다.

게다가 서류에 날짜나 순서가 적혀 있지 않아, **"어떤 서류를 먼저 읽어야 하는지"**, **"이게 언제 작성된 것인지"** 아무도 알 수 없는 상태였습니다.

그래서 이번 작업은 다음 세 가지를 완벽하게 정돈한 것입니다:
1. **서랍 통일 (docs/ 폴더 통일)**: 모든 방마다 서류는 무조건 docs(문서 보관함)라는 하나의 서랍에 넣도록 통일했습니다. 서랍이 없던 방에는 새 서랍을 자동으로 만들어 주었습니다.
2. **이름표와 목차 달기 (시간순 정렬 & README.md 색인)**: 서랍 속 문서들에 시간순으로 1_, 2_ 번호표를 달고, 서랍 입구에 "이 서랍에는 무슨 서류가 들어있는지" 한눈에 보여주는 목차(Index README)를 붙였습니다.
3. **가정부 3인방의 영구 규칙 제정 (3대 AI 도구 글로벌 룰 고정)**: 우리 서재를 관리하는 3명의 똑똑한 AI 집사(Antigravity, Claude Code, Codex)에게 **"앞으로 새 문서를 만들 때는 반드시 해당 방의 docs/ 서랍에 넣고, 목차를 갱신하라"**는 규칙을 영구히 머릿속(글로벌 헌법)에 입력해 두었습니다.

## 2. 🔍 심층 진단: 왜 단순하게 번호만 붙이면 위험했을까? (DEEPDIVE & CRITIC & REDTEAM)

겉보기에는 단순히 파일 이름 앞에 0_, 1_을 붙이면 될 것 같았지만, 소프트웨어 아키텍처 관점(System Architecture)에서 실측 조사를 진행한 결과 **숨겨진 4가지 치명적인 함정(Blindspots)**이 드러났습니다:

### ① 병행 충돌의 맹점 (Concurrency Race Condition)
- **실제 발견된 증거**: 실제로 c3p-council-orchestrator/docs/ 폴더를 실측해 보니, 과거에 두 개 이상의 AI가 동시에 작업하면서 0_ 2개, 1_ 2개, 2_ 2개, 3_ 2개 등 **똑같은 번호표를 가진 중복 문서**들이 충돌해 있었습니다.
- **원인**: 여러 에이전트가 동시에 글을 쓰면, 둘 다 "내가 07번을 쓸 차례구나!" 하고 똑같은 번호를 채택하기 때문입니다.

### ② 연쇄 재명명 지옥 (Cascade Renaming Hell)과 링크 파손
- **문제점**: 만약 1_과 2_ 사이에 새로운 보충 문서를 끼워 넣어야 한다면, 뒤에 있는 50개 문서의 번호를 3 -> 04, 4 -> 05로 전부 고쳐야 합니다.
- **위험도**: 워크스페이스 안에는 다른 문서를 가리키는 **374개의 마크다운 연결 링크(Cross-links)**가 있었습니다. 파일 이름이 바뀌면 이 374개의 링크가 전부 끊어져 "페이지를 찾을 수 없습니다(404 Broken Link)" 오류가 발생합니다.

### ③ 문서의 수명 주기(Lifecycle) 구분 무시
- 문서는 두 종류가 있습니다:
  - **기록 문서(Timeline Docs)**: 특정 날짜의 회의록, 보고서, 실험일지 -> 날짜(YYMMDD_)나 번호(1_)가 필수적임.
  - **영속 지침(Living Guides)**: 프로그램 사용법, 환경설정 매뉴얼 -> 수시로 업데이트되므로 번호 대신 고유한 이름(nvironment-desktop.md)이 있어야 함.

### ④ 3대 AI 글로벌 룰의 엄격한 글자수 상한선 (Character Ceiling)
- Antigravity 도구의 글로벌 룰에는 **최대 11,600글자**라는 엄격한 상한선이 설정되어 있습니다.
- 작업 시작 전 실측치는 **11,568글자**로, 한도까지 **단 32글자**만 남아 있었습니다.
- 긴 문장을 무턱대고 추가하면 즉시 11,600글자를 초과하여 시스템 자동 진단(Harness Test)이 붕괴(Fail)하는 구조였습니다.

## 3. 💡 전문적 최적화 해결책 (EXPERT & OPTIMIZE)

위 4가지 함정을 해결하기 위해 고도화된 정제 기법을 적용했습니다:

### 1) 글로벌 룰 초압축 리팩토링 (Token & Budget Optimization)
- shared/global-rules/core.md의 제5조(P5. Workspace and repository organization)를 문맥 손실 없이 고밀도로 다듬어:
  - 기존 11,568글자에서 **11,534글자**로 오히려 34글자를 순감(줄임)시켰습니다.
  - 이를 통해 <section>/docs/ 원칙을 헌법에 완벽히 새겨 넣으면서도, 안전 마진을 기존 32글자에서 **66글자**로 2배 이상 넓혔습니다.

### 2) 하이브리드 명명 및 인덱스 체계 (Hybrid Naming & Index Protocol)
- **물리적 파일명**: 기록 문서는 1_, 2_ 및 날짜(YYMMDD_)를 병기하여 안정성을 확보하고, 영속 매뉴얼은 시맨틱 케밥케이스([topic].md)를 유지했습니다.
- **논리적 순서 관리**: 물리적 파일명을 억지로 뒤흔드는 대신, 각 docs/ 서랍마다 **색인표(docs/README.md)**를 두어 사용자와 AI가 언제나 완벽한 시간순·중요도순으로 읽을 수 있게 만들었습니다.

### 3) 374개 연결 링크 전수 자동 보정 (Link Integrity Automation)
- git mv를 사용하여 파일의 과거 히스토리(Commit History)를 보존하며 이동시켰습니다.
- 파일이 docs/ 서랍 안으로 한 단계 깊숙이 들어감에 따라 변경된 상대 경로(../)를 파싱하여 전수 수정, 이동된 섹션의 **깨진 링크 수를 0건**으로 복구했습니다.

- **깔끔한 방바닥**: 각 섹션의 루트 폴더에는 오직 첫 진입용 README.md와 필수 도구 설정만 남아 언제나 쾌적하고 투명한 구조가 유지됩니다.

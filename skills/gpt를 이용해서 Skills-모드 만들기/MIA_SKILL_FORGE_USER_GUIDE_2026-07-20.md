# GPT 챗봇을 Agent Skill 후보로 바꾸는 법

> 대상: “Skill이 정확히 무엇인지, 무엇을 물어봐야 하는지도 아직 잘 모르겠다”는 사용자

## 먼저 한 문장으로 이해하기

`mia-skill-forge`는 ChatGPT용 챗봇이나 긴 프롬프트 설계를 Claude Code·Codex·Antigravity에서 사용할 수 있는 Agent Skill(에이전트 업무 설명서) 후보로 정리하는 제작 도구다.

완성품을 즉시 설치하는 도구가 아니라, 안전하게 검토하고 시험할 수 있는 후보를 만드는 도구라고 이해하면 된다.

## 왜 필요한가

ChatGPT 챗봇 지시문을 다른 AI 도구에 그대로 붙여 넣으면 다음 문제가 생길 수 있다.

- ChatGPT에서만 통하는 기능이나 표현이 섞인다.
- 지시문이 너무 길어 필요한 규칙을 찾기 어렵다.
- 설치·배포·삭제 같은 위험한 행동의 승인 경계가 흐려진다.
- 문서가 그럴듯하다는 이유만으로 실제 작동도 검증됐다고 착각하기 쉽다.
- Codex·Claude Code·Antigravity용 복사본이 서로 다르게 변한다.

`mia-skill-forge`는 원본을 통째로 복사하지 않고, 필요한 규칙만 골라 공통 구조로 다시 만든다.

## 꼭 알아둘 네 가지 말

다음 네 가지를 구분하면 제작 결과를 과대평가하지 않고 읽을 수 있다.

| 용어 | 쉬운 뜻 |
|---|---|
| Skill | AI가 특정 일을 일관되게 수행하도록 알려주는 작은 업무 설명서 |
| 후보 | 아직 실제 환경에서 충분히 시험하지 않은 초안 |
| 정적 검사 | 파일 구조·이름·링크·위험 명령처럼 실행하지 않고 확인할 수 있는 검사 |
| 런타임 평가 | 실제 AI 도구에서 호출해 원하는 행동을 하는지 확인하는 시험 |

정적 검사를 통과했다고 실제 작동까지 보장되는 것은 아니다. 자동차 설계도 검토와 실제 주행 시험이 다른 것과 같다.

## 현재 만드는 과정

```text
원본 GPT·챗봇·문서
        ↓
필요한 규칙과 버릴 규칙 구분
        ↓
공통 Agent Skill 후보 제작
        ↓
파일 구조와 안전 규칙 검사
        ↓
실제 AI 도구에서 발동·행동 시험
        ↓
통과한 경우에만 설치·승격 검토
```

현재 저장소의 `mia-skill-forge`는 **후보 제작과 정적 검사 단계**까지 구현됐다. 전역 설치나 세 도구의 실제 발동 시험은 아직 하지 않았다.

## 사용자는 무엇을 준비하면 되는가

완벽한 기획서를 만들 필요는 없다. 다음 중 아는 것만 제공하면 된다.

- 바꾸고 싶은 GPT·챗봇·프롬프트·설계 문서
- 이 도구가 가장 잘해야 하는 한 가지 일
- 누가 사용할지
- 사용하면 안 되는 상황
- 원하는 대상: Codex, Claude Code, Antigravity 또는 세 도구 모두

모르는 항목은 “모름”이라고 적어도 된다. 결과를 크게 바꾸는 정보가 없을 때만 AI가 한 가지 핵심 질문을 한다.

## 이렇게 요청하면 된다

가장 간단한 요청:

```text
$mia-skill-forge 이 GPT 설계를 세 도구 공통 Skill 후보로 만들어줘.
가장 중요한 일은 사용자의 구현 계획을 검토하는 것이야.
```

아직 정리가 안 된 경우:

```text
$mia-skill-forge 이 챗봇을 Skill로 바꾸고 싶은데 무엇부터 정해야 하는지 모르겠어.
초보자에게 필요한 질문부터 한 개씩 해줘.
```

기존 Skill을 개선하려는 경우:

```text
$mia-skill-forge 이 Skill의 최적화 수행 절차를 적용해줘.
현재 파일을 기준선으로 보존하고, 바꿀 근거가 있는 부분만 수정해줘.
```

## 최적화는 어떻게 진행되는가

최적화는 무조건 줄이거나 새로 쓰는 작업이 아니다.

1. **목표 잠금:** 무엇을 개선할지와 건드리지 않을 범위를 정한다.
2. **기준선 저장:** 현재 파일의 해시와 대표 사용 사례를 기록한다.
3. **한 가지 병목 선택:** 발동·결과·안전·문서 크기·플랫폼 차이 중 가장 중요한 문제 하나를 고른다.
4. **대안 비교:** 그대로 유지, 단순화, 부분 수리, 책임 분리 중 가장 작은 대안을 선택한다.
5. **후보에서 수정:** 정본을 바로 덮어쓰지 않고 별도 후보에서 바꾼다.
6. **층별 검사:** 구조 검사부터 실제 발동 시험까지 싼 검사부터 진행한다.
7. **판정:** 반복 개선, 확대 적용, 중단, 변경 없음 중 하나를 선택한다.

근거가 부족하면 **변경 없음**이 올바른 최적화 결과일 수 있다.

## 규칙 추적표를 읽는 법

원본 챗봇이나 기존 Skill의 문장을 그대로 옮기지 않는다. 각 규칙은 다음 셋 중 하나로 기록한다.

- `preserve`: 다른 도구에서도 그대로 필요한 규칙
- `adapt`: 목적은 유지하되 대상 도구에 맞게 바꾼 규칙
- `omit`: 개인 지시문, 특정 도구 전용 기능, 중복처럼 후보에 넣지 않는 항목

## 결과 상태 읽는 법

| 표시 | 사용자가 이해할 뜻 |
|---|---|
| `STATIC_CANDIDATE` | 후보 파일을 만들었지만 실제 작동은 아직 모름 |
| `STRUCTURE_VALIDATED` | 파일 구조 검사는 통과했지만 행동은 아직 모름 |
| `RUNTIME_EVALUATED` | 지정한 AI 도구에서 실제 사례를 시험함 |
| `VERIFIED_RESULT` | 미리 정한 행동·안전·플랫폼 기준을 모두 증거와 함께 통과함 |

중간 단계를 건너뛰고 `VERIFIED_RESULT`라고 표시하면 안 된다.

## 자동으로 하지 않는 일

다음 행동은 별도 승인이 있어야 한다.

- 사용자 전역 Skill 폴더에 설치
- 기존 정본 덮어쓰기
- Git 커밋과 원격 저장소 푸시
- 배포·공개·계정 또는 권한 변경
- 파일 삭제나 복구하기 어려운 작업

이번 작업의 커밋과 푸시는 사용자가 명시적으로 승인했기 때문에 진행할 수 있다. 전역 설치는 승인 범위에 포함되지 않는다.

## 현재 결과와 다음 단계

현재 확보된 것:

- `mia-skill-forge` 후보
- MIA 품질 규칙, 세 플랫폼 계약, 출력 계약, 최적화 수행 절차
- 오류를 자동으로 찾는 정적 감사 스크립트
- 정상·오류 표본과 향후 런타임 평가 양식

아직 확인하지 않은 것:

- 실제 Codex에서 의도한 문장으로 정확히 발동하는가
- 평범한 Skill 제작 요청에서 잘못 발동하지 않는가
- Claude Code와 Antigravity에서도 같은 의미로 동작하는가
- 기존 `plan-review-execute`보다 실제 결과가 좋아지는가

다음 단계는 기존 `plan-review-execute`를 첫 표본으로 사용해 **바꿀 근거가 있는지 먼저 측정하는 것**이다. 측정 결과가 없다면 정본은 유지한다.

## 자주 생기는 오해

### 문서가 길수록 좋은 Skill인가

아니다. AI가 실제 업무에 필요한 규칙을 빨리 찾을 수 있어야 한다. 긴 배경 설명은 별도 참고 문서로 분리하고 정상 실행 절차는 짧게 유지한다.

### 세 도구용 파일을 각각 만들면 끝인가

아니다. 파일이 존재하는 것과 세 도구에서 같은 행동을 하는 것은 다르다. 각 도구에서 발동·비발동·대표 작업·안전 거부를 시험해야 한다.

### 정적 감사 오류가 0이면 바로 설치해도 되는가

아니다. 구조가 깨지지 않았다는 뜻일 뿐이다. 실제 행동 평가와 사용자 승인이 남아 있다.

# Slash Prompt Modes 설계·진단·수정·검증 전체 과정

## 한 문장 결론

`/OPTIMIZE` 같은 짧은 명령을 세 AI 도구에서 같은 뜻으로 사용하기 위해, 하나의 정본에서
플랫폼별 얇은 어댑터를 만들고 **설치 확인과 실제 동작 확인을 따로 시험**했습니다.

최종적으로 Antigravity·Claude Code·Codex에서 대문자와 소문자 명령 인식을 확인했습니다.
다만 이것은 명령이 선택되는지를 검증한 결과이며, 모든 실제 과제에서 답변 품질이 반드시
향상된다는 뜻은 아닙니다.

## 이 작업은 무엇을 해결했나요?

원본 문서 `p1. GPT 실전 치트키 모드.md`에는 `/CRITIC`, `/OPTIMIZE`, `/SELFREFINE`처럼
AI의 작업 방식을 바꾸는 아이디어가 있었습니다. 목표는 이 아이디어를 다음 조건을 갖춘
독립 Skill로 만드는 것이었습니다.

1. MIA를 호출하지 않아도 독립적으로 작동할 것
2. 명령 앞에 `/`가 있을 때만 발동할 것
3. Antigravity·Claude Code·Codex에 같은 의미로 적용할 것
4. 대문자와 소문자를 같은 명령으로 취급할 것
5. 설치됐다는 사실과 실제로 작동했다는 사실을 혼동하지 않을 것
6. 모르는 것을 무엇부터 물어봐야 할지 모르는 사용자도 사용할 수 있을 것

## 먼저 알아둘 다섯 가지

| 용어 | 쉬운 뜻 |
|---|---|
| 정본(Canonical Source) | 여러 복사본의 기준이 되는 원본 한 벌 |
| 어댑터(Adapter) | 같은 정본을 각 AI 도구가 알아듣는 형식으로 연결하는 얇은 변환층 |
| 정적 검사(Static Check) | 파일·이름·해시·구조가 맞는지 실행하지 않고 확인하는 검사 |
| 런타임 검사(Runtime Check) | AI 도구를 실제로 실행해 명령이 인식되는지 확인하는 검사 |
| 회귀 테스트(Regression Test) | 고친 문제가 나중에 다시 생기지 않도록 자동으로 막는 시험 |

비유하면 정적 검사는 “리모컨에 배터리가 들어 있고 버튼이 붙어 있는지” 보는 일이고,
런타임 검사는 “실제로 전원 버튼을 눌러 TV가 켜지는지” 보는 일입니다.

## MIA 4단계로 본 전체 수행 과정

### 1. 기획(Frame): 성공 조건을 먼저 고정

성공을 “파일이 복사됨”으로 두지 않았습니다. 다음처럼 관찰 가능한 조건으로 나눴습니다.

- 10개 정본 토큰이 존재한다.
- 대문자와 소문자가 같은 정본 토큰으로 정규화된다.
- 슬래시 없는 일반 자연어는 이 Skill을 발동하지 않는다.
- 여러 모드를 함께 쓰면 하나가 사라지지 않는다.
- 세 플랫폼 설치본이 같은 정본에서 생성된다.
- 미실행·예산 초과·권한 거부는 성공으로 기록하지 않는다.

### 2. 검토(Review): 세 가지 구조를 비교

| 대안 | 장점 | 문제 | 판정 |
|---|---|---|---|
| 플랫폼마다 완전한 Skill을 따로 작성 | 각 도구에 맞추기 쉬움 | 내용이 세 벌로 갈라져 시간이 지나면 서로 달라짐 | No-Go |
| 공통 본체만 설치 | 정본은 하나 | Claude Code의 대문자 `/OPTIMIZE`가 거부됨 | No-Go |
| 공통 정본 + 생성된 얇은 어댑터 | 의미는 한곳에서 관리하면서 플랫폼 차이 흡수 | 생성기와 동기화 검사가 필요 | Go |

선택한 구조는 `slash-prompt-modes` 정본, 소문자 Skill 별칭 10개, Claude Code 대문자
호환 command 10개입니다.

### 3. 실행(Execute): 작은 수정과 실패 기반 개선

#### 문제 1 — 이름만 보고 기능을 알기 어려움

처음의 상위 이름 후보 `prompt-tools`는 너무 넓었습니다. 사용자가 폴더만 보고도 내용을
짐작할 수 있도록 `slash-prompt-modes`로 정했습니다.

#### 문제 2 — Claude Code가 대문자 명령을 거부

Claude Code 실동작에서 `/OPTIMIZE`가 `Unknown command`로 거부됐습니다. 소문자 Skill만으로
대문자 명령까지 보장한다고 주장할 수 없었습니다.

수정은 Claude Code 전용 대문자 호환 command를 정본에서 생성하는 방식으로 했습니다.
그 뒤 최종 검증에서 `Unknown command`는 0건이었습니다.

#### 문제 3 — 생성 파일에 실제 토큰 대신 PowerShell 내부 문자열이 남음

별칭 생성 결과에 `/CRITIC` 같은 값 대신
`$(System.Collections.Hashtable.Token)`이 남는 의미 결함이 발견됐습니다. 파일 개수와 해시는
맞았지만 내용은 틀린 사례입니다.

생성기를 고치고, 10개 별칭에 실제 토큰이 들어가는지와 `$(` 같은 미해석 표현식이 남지
않는지를 검사하는 회귀 테스트를 추가했습니다.

#### 문제 4 — 별칭이 다른 파일 읽기에 지나치게 의존

최초 Codex 탐침은 스킬 목록에 표시된 축약 루트 `r0`를 실제 폴더명으로 오해해 파일 읽기에
실패한 뒤 검색으로 복구했습니다. Claude Code 일부 탐침도 읽기 도구가 없거나 호출 예산이
부족하면 상세 계약을 읽지 못했습니다.

해결책은 별칭 안에 짧은 “최소 계약”을 포함하는 것이었습니다. 복잡한 과제에서만 상세
정본을 추가로 읽고, 단순한 과제에서는 별칭 자체만으로 모드의 정체성과 핵심 행동을 유지합니다.

#### 문제 5 — 같은 계약이 두 생성기에 중복됨

소문자 별칭 생성기와 Claude 대문자 command 생성기에 같은 문장을 따로 적으면 한쪽만 고칠
위험이 있습니다. 10개 이름·정본 토큰·발동 조건·최소 계약을
`references/mode-manifest.json` 한 파일로 모았습니다.

두 생성기가 이 파일을 읽기 때문에 계약 변경은 한곳에서 시작합니다.

#### 문제 6 — Windows PowerShell 5.1에서 한글이 손상됨

새 매니페스트는 BOM 없는 UTF-8 JSON입니다. Windows PowerShell 5.1의 기본 읽기 방식으로는
한글이 시스템 문자셋으로 잘못 해석돼 테스트가 실패했습니다.

`[IO.File]::ReadAllText(..., UTF8)`로 문자 인코딩을 명시했습니다. PowerShell 7뿐 아니라
Windows PowerShell 5.1을 사용하는 회귀 테스트도 통과했습니다.

#### 문제 7 — 평가기가 실제 실패보다 더 많이 실패로 셈

최초 평가기는 `MODE=CRITIC`과 `MODE=/CRITIC`을 서로 다른 값으로 보았습니다. 정본 의미는
같지만 출력 문자열만 다른 사례입니다. 이 때문에 Codex 최초 결과가 엄격 기준 6/20으로
보였습니다.

평가기를 수정해 선행 `/` 유무는 정규화했습니다. 반면 `/STRUCTURED FEW-SHOT`이
`/STRUCTURED`로 줄어드는 경우는 의미가 달라지므로 계속 실패로 처리했습니다.

#### 문제 8 — Antigravity 실행 수단이 없다는 잘못된 중간 판단

셸 PATH에서 `antigravity`, `gemini`, `gemini-cli`를 찾지 못해 처음에는 런타임 검증이
불가능하다고 판단했습니다. 하지만 도구 목록을 더 확인하자 `antigravity-bridge`가
`agy 1.1.27`을 호출할 수 있었습니다.

샌드박스·계획 모드·자동승인 해제 조건으로 실행해 대·소문자 20/20을 확인했습니다.
따라서 “PATH에 명령이 없음”과 “실행 경로가 전혀 없음”은 다른 사실임을 기록했습니다.

#### 문제 9 — 안전한 음성 시험에서 불필요한 관리자 도구 요청

Antigravity의 첫 슬래시 없는 음성 사례는 모델이 불필요한 관리자 권한 도구를 요청했고,
헤드리스 안전 모드가 이를 거부해 결과를 내지 못했습니다. 권한을 우회하지 않았습니다.

도구가 필요 없는 순수 트리거 판정 문장으로 한 번만 재시도해 `MODE=NONE`을 확인했습니다.
최초 실패도 지우지 않고 증거에 남겼습니다.

### 4. 검증(Verify): 무엇이 실제로 확인됐나

| 검증 대상 | 결과 |
|---|---|
| Antigravity 10모드 × 대·소문자 | 20/20 |
| Codex 최종 소문자 별칭 | 10/10 |
| Claude Code 최종 소문자 별칭 | 10/10, 한 사례는 예산 상향 재시도 |
| Claude 대문자 `STRUCTURED FEW-SHOT` 수정 사례 | 1/1 |
| Claude `Unknown command` | 0건 |
| 세 도구의 슬래시 없는 비발동 | 통과 |
| 세 도구의 `/critic /OPTIMIZE` 조합 | 통과 |
| 생성기·라이선스 회귀 테스트 | 9/9 |
| 세 플랫폼 설치 대상 정본 일치 | 43개 모두 일치 |
| 저장소 전체 검사 | `npm run check` exit 0 |

## 비판적 최종 판정

| 판정 | 근거 | 영향 | 수정 또는 유지 결정 |
|---|---|---|---|
| 설치 성공과 실동작 성공을 처음에는 충분히 분리하지 못함 | 과거 단발 `/OPTIMIZE` 결과가 전체 검증처럼 보일 수 있었음 | 과장된 완료 보고 위험 | 설치 무결성과 런타임 결과를 다른 JSON으로 분리 |
| 구조·해시 검사만으로 의미 결함을 잡지 못함 | PowerShell 내부 문자열이 생성본에 남음 | 모든 플랫폼에 같은 잘못된 내용이 복제될 수 있음 | 실제 토큰과 미해석 표현식을 검사하는 회귀 테스트 추가 |
| 평가기 자체도 검증 대상이어야 함 | 선행 `/` 차이로 정상 출력을 실패 처리 | 거짓 실패율 증가 | 의미 정규화와 파서·토큰·계약 관측을 분리 |
| 플랫폼 실행 경로 탐색이 불완전했음 | Antigravity bridge를 뒤늦게 발견 | 미검증 상태가 불필요하게 지속 | PATH뿐 아니라 사용 가능한 브리지·도구 목록도 확인 |
| 트리거 검증은 품질 검증이 아님 | 시험은 모드 이름 인식 중심 | 실제 글쓰기·코딩 품질 향상을 일반화할 수 없음 | 품질 검증 상태는 계속 `false`로 유지 |

## 현재 보장하는 것과 보장하지 않는 것

보장 범위:

- 문서화된 대문자와 소문자 양 끝 표기
- 10개 모드의 정본 토큰 인식
- 슬래시 없는 일반 자연어의 비발동
- 시험한 두 모드 혼합 조합
- 세 플랫폼 설치본과 생성 정본의 일치

아직 보장하지 않는 범위:

- `/OpTiMiZe` 같은 임의 혼합 대소문자
- 모든 장문 대화에서의 오발동 부재
- 모든 실제 업무에서의 품질 향상
- 모델·CLI 버전이 바뀐 뒤에도 자동으로 같은 결과가 유지됨

그래서 최종 상태는 다음처럼 분리합니다.

```text
cross_platform_trigger_matrix_verified = true
cross_platform_behavioral_quality_verified = false
```

## 사용자가 직접 다시 확인하는 가장 짧은 순서

1. 정본과 설치본이 같은지 검사합니다.

   ```powershell
   ./scripts/sync-slash-prompt-modes.ps1 -Mode Check
   ```

2. 생성기와 저장소 규칙을 검사합니다.

   ```powershell
   npm run skills:test
   npm run check
   ```

3. 필요한 플랫폼·표기만 런타임 검사합니다. 실제 모델 호출 비용이 발생할 수 있습니다.

   ```powershell
   ./scripts/run-runtime-matrix.ps1 -Platform Codex -CaseFilter lower
   ./scripts/run-runtime-matrix.ps1 -Platform ClaudeCode -ModeFilter structured -CaseFilter upper -ClaudeMaxBudgetUsd 0.25
   ```

4. 결과 JSON에서 `passed`, `failed`, `unknown_command`를 확인합니다.

   출력 파일은 기본적으로 `validation-evidence/runtime-matrix-<플랫폼>-<실행시각>.json`
   형식으로 생성돼 이전 실행 결과를 덮어쓰지 않습니다.

5. 한 사례가 예산·네트워크·권한 때문에 실패했다면 명령 결함과 실행 환경 실패를 구분합니다.
   같은 원인으로 무제한 재시도하거나 권한을 우회하지 않습니다.

## 실패했을 때 확인할 순서

1. `Unknown command`가 있으면 명령 이름과 Claude 대문자 command 설치를 확인합니다.
2. 종료 코드가 1이고 응답이 비어 있으면 예산·네트워크·권한 오류를 확인합니다.
3. `/STRUCTURED`만 반환되면 첫 인수 `FEW-SHOT`이 유지됐는지 확인합니다.
4. 생성 파일에 `$(` 또는 `System.Collections.Hashtable`이 있으면 생성기를 다시 검사합니다.
5. 한 플랫폼만 다르면 설치본을 직접 수정하지 말고 정본에서 다시 생성·동기화합니다.

## 롤백과 보존

전역 설치 교체 전 백업을 만들었습니다.

```text
~/.agent-skill-backups/slash-prompt-modes-20260905-202038
```

다른 세션의 파일과 사용자 데이터는 커밋에 포함하지 않았습니다. Git push 전에는 항상
`HEAD`와 `origin/main`의 분기 여부를 확인했고, 다른 세션 커밋이 먼저 원격에 올라갈 때까지
기다린 뒤 이번 작업 경로만 명시적으로 스테이징했습니다.

## 다음에 더 검증할 가치가 있는 것

가장 유용한 다음 실험은 “명령을 알아봤는가”가 아니라 “실제 결과가 더 좋아졌는가”입니다.
같은 입력·모델·설정을 사용해 모드 없는 기준선과 모드 사용 결과를 최소 3회 비교해야 합니다.
정확성, 요구사항 충족, 안전 실패, 비용과 지연을 함께 측정해야 하며 품질만 보고 비용이나
안전 악화를 무시하면 안 됩니다.

그 실험이 통과하기 전에는 `cross_platform_behavioral_quality_verified`를 `true`로 바꾸지
않습니다.

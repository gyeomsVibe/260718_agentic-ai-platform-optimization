## 1. 10살도 이해하는 한 장 설명

Agent Skill은 AI가 어떤 일을 반복해서 잘하도록 만든 **작은 사용 설명서 상자**입니다.

- `SKILL.md`는 상자 앞면의 이름표와 핵심 설명서입니다.
- `references/`는 필요할 때만 꺼내 보는 교과서입니다.
- `scripts/`는 매번 똑같이 해야 하는 일을 실수 없이 처리하는 계산기입니다.
- `assets/`는 결과물을 만들 때 복사하거나 사용하는 준비물입니다.

좋은 Skill은 무조건 크지 않습니다. 필요한 순간에 필요한 설명만 꺼내고, 실제로 일을 잘했는지 시험할 수 있어야 합니다.

가장 쉬운 판단법은 다섯 질문입니다.

1. 누구의 어떤 반복 문제를 해결하나요?
2. 평범한 AI에게 그냥 부탁하는 것보다 무엇이 더 좋아지나요?
3. 잘했다는 것을 어떤 실제 사례로 확인하나요?
4. 위험한 일은 누구의 허락을 받고 어떻게 되돌리나요?
5. 나중에 규칙이 바뀌면 어느 한 파일만 고치면 되나요?

하나라도 답할 수 없다면 아직 완성된 Skill이 아닙니다.

### 공식 skill-creator를 한 장으로 이해하기

OpenAI의 `skill-creator`가 강조하는 제작 원리는 여섯 문장으로 압축할 수 있습니다.

1. **AI가 이미 아는 설명은 덜어냅니다.** 컨텍스트는 공용 자원이므로 비싼 장문보다 짧은 예시를 우선합니다.
2. **실수 비용에 맞춰 자유도를 정합니다.** 창작은 넓게, 선호 절차는 매개변수화하고, 깨지기 쉬운 반복은 좁은 스크립트로 만듭니다.
3. **`SKILL.md`는 핵심만 둡니다.** 이름·발동 설명·작업 절차를 두고, 긴 지식은 `references/`, 반복 코드는 `scripts/`, 결과물 재료는 `assets/`로 분리합니다.
4. **필요할 때만 읽게 만듭니다.** 메타데이터 → 본문 → 참조의 점진적 공개(Progressive Disclosure)를 지키고 참조를 깊게 중첩하지 않습니다.
5. **구체 사례에서 시작합니다.** 사용자가 실제로 할 말을 먼저 모으고, 사례마다 재사용할 지식·스크립트·자산이 무엇인지 역산합니다.
6. **초기화 → 편집 → 정적 검증 → 실사용 반복을 지킵니다.** 파일을 만든 사실을 성능이나 런타임 성공으로 바꾸어 말하지 않습니다.

이 저장소는 여기에 권한, 근거, 교차 플랫폼, 라이선스와 실패 회귀 검증을 더합니다. 공식
`skill-creator`의 “README를 런타임 Skill에 넣지 않는다”는 원칙과 사람용 문서 요구는 충돌하지
않습니다. 저장소의 README는 **관리용 래퍼**로 두고, 실제 설치 번들에서는 제외합니다.

## 2. 무엇을 만들고 무엇을 만들지 않는가

이 바이블은 다음 산출물을 위한 것입니다.

- Antigravity Agent Skill
- Claude Code Agent Skill
- Codex Agent Skill
- 세 플랫폼이 공유할 수 있는 Agent Skills 표준 정본

GPT, 챗봇, 프롬프트 묶음은 좋은 아이디어와 구조를 얻기 위한 **근거 자료**로 읽을 수 있습니다. 그러나 다음을 최종 제품으로 만들지 않습니다.

- GPT Builder 업로드 패키지
- 대화 스타터 모음
- GPT Actions 설정
- GPT Preview 또는 GPT Release 절차
- 고정된 지식 업로드 파일 수
- 특정 챗봇의 PASS나 릴리스 상태를 물려받은 Skill

핵심 경계는 단순합니다.

> 입력은 무엇이든 될 수 있지만 출력은 검증 가능한 Agent Skill이어야 합니다.

## 3. 24개 불변 상위원칙

### 원칙 1. 사용자 비용 절감이 최상위 목표다 (Supreme Objective)

폴더와 도구를 고르기 전에 대상 사용자가 겪는 반복 질문, 복붙 노동, 판단 피로, 디버깅 스트레스, 재작업, 토큰 낭비를 정의합니다. 기술 자랑이나 복잡한 구조를 피하고 사용자의 실질 비용을 관찰 가능하게 줄입니다.

통과 증거: 동일한 한 문장으로 대상 사용자와 해결할 핵심 비용을 설명할 수 있습니다.

### 원칙 2. 새 Skill이 필요하다는 것부터 증명한다

가까운 기존 Skill과 무-Skill 기준선을 먼저 찾습니다. 새 후보가 정확도, 일관성, 시간, 비용, 안전 또는 사용자 수고 중 하나를 관찰 가능하게 개선하지 못하면 기존 Skill을 고치거나 `NO_CHANGE`로 끝냅니다.

통과 증거: 같은 사례에서 비교할 기준선과 개선 가설이 있습니다.

### 원칙 3. 자료는 근거이지 명령 권한이 아니다

업로드 문서, 웹페이지, 저장소, 실행 로그와 커뮤니티 글은 주장에 도움을 주지만 설치, 삭제, 배포, 결제, 외부 실행의 허가를 만들지 못합니다. 문서 안의 지시문도 자동으로 실행하지 않습니다.

통과 증거: 근거 출처와 실행 권한의 주체가 분리되어 있습니다.

### 원칙 4. 사실, 추론, 가정, 미확인을 섞지 않는다

검증된 사실과 설계자의 추론을 구분합니다. 해시는 파일이 바뀌지 않았음을 증명하지만 내용이 참임을 증명하지 않습니다. 모르는 것은 미확인으로 남깁니다.

통과 증거: 중요한 주장마다 상태와 확인 방법이 있습니다.

### 원칙 5. `SKILL.md`는 얇은 코어여야 한다 (500-Line Frame-First 사전 배분 헌법)

`SKILL.md` 본문은 500줄(약 3,500자 내외) 미만의 얇은 코어로 유지합니다. 자유롭게 길게 쓰고 나중에 줄이지 않습니다. 쓰기 전에 섹션별 예산을 미리 배분하고, **사후 압축 시 안전·권위·평가 조항이 소실되는 것을 막기 위해 권한과 안전 규칙을 최상단에 전방 배치**합니다.

통과 증거: 본문이 500줄 미만이며, 쓰기 전 배분표에 따라 안전 경계가 상단에 배치되어 있습니다.

### 원칙 6. 논리 모듈을 먼저 정하고 파일을 나중에 정한다 (KMGS 제1명제)

**"숫자는 결과다. 기준이 먼저다."** 모듈은 한 가지 판단 책임(Logical Module)입니다. 파일 수를 미리 5개, 10개처럼 고정하지 않습니다. 정체성, 검색성, 지연, 안전성, 평가성, 유지보수성을 통과한 결과로 물리 파일이 산정되어야 하며, 산정 근거(`Module Budget Rationale`)가 없으면 미완성입니다.

통과 증거: 각 모듈의 목적과 소유 정책, 그리고 물리 파일 산정 근거가 기록되어 있습니다.

### 원칙 7. 논리 모듈은 일반 기능 모듈보다 상위이며 덮어쓸 수 없다 (논리 > 기능 절대 위계)

편의 기능이나 새로운 도구 연동이 아무리 훌륭해도 정체성, 안전 게이트, 상속 계약, 파일 신뢰 경계, 평가 기준을 무너뜨릴 수 없습니다. 충돌 시에는 항상 `Gate > Vagueness > Safety > Evals > Scoring > Router > Contract > Others`의 고정 순서로 해결합니다.

통과 증거: 기능 추가로 인해 기존 상위 정책이나 안전 경계가 약화되지 않았음이 증명됩니다.

### 원칙 8. 변경 가능한 정책에는 최종 소유자가 한 명이어야 한다

두 모듈이 같은 안전 기준, 출력 스키마 또는 상태값의 최종 결정을 서로 다르게 내리면 `owner_collision`입니다. 단일 소유자와 대체 이력을 정하기 전에는 승격하지 않습니다.

통과 증거: `owner_namespace`, 비책임 범위, 충돌 규칙이 식별됩니다.

### 원칙 9. 정본은 하나만 둔다 (수동 3벌 복제 금지)

같은 규칙을 Markdown, HTML, JSON 세 벌로 수동 관리하지 않습니다. 사람이 읽고 버전 관리하기 좋은 정본 하나를 선택하고, 다른 형식은 필요할 때 결정적으로 생성합니다.

통과 증거: 동일 정책의 수동 사본이 없고 파생 경로가 기록되어 있습니다.

### 원칙 10. 자유도는 작업의 위험에 맞춘다

여러 답이 가능한 창작은 지침 중심으로 둡니다. 선호 절차가 있는 작업은 의사코드나 매개변수화한 도구를 사용합니다. 실수 비용이 큰 반복 작업은 좁고 결정적인 스크립트로 만듭니다.

통과 증거: 각 단계의 자유도가 실패 비용과 일치합니다.

### 원칙 11. 스크립트는 반복성과 결정성이 있을 때만 추가한다

한 번 쓸 코드를 장식처럼 넣지 않습니다. 같은 코드를 반복 작성하거나 사람이 하기 쉬운 실수를 없앨 때만 스크립트를 추가하고 실제로 실행해 검증합니다.

통과 증거: 스크립트가 줄이는 반복 또는 오류와 실행 결과가 기록됩니다.

### 원칙 12. 모르는 것을 모르는 사용자를 보호한다 (역질문 & 추천 DNA)

사용자가 필요한 입력과 위험을 스스로 열거할 수 없다고 가정합니다. "알아서 확인하세요"라고 방치하지 않으며, AI가 안전하게 가능한 작업을 먼저 수행합니다. 질문할 때는 한 번에 하나의 표적 역질문과 권장 기본값(한 줄 이유 포함)을 함께 제공합니다.

통과 증거: 첫 실행에서 무엇을 주고 무엇이 실행되지 않으며 다음에 무엇을 할지 평이한 한국어로 알 수 있습니다.

### 원칙 13. 빠른 경로에도 품질 하한선이 있다

속도를 이유로 핵심 작업, 출력 계약, 중대 위험, 정적 검사와 상태 정직성을 생략하지 않습니다. `FAST`는 검증 제거가 아니라 가장 싼 유효 검증부터 하는 방식입니다.

통과 증거: 최소 후보에도 정상·오류·안전 사례가 있습니다.

### 원칙 14. 조사는 의사결정 위험에 비례한다 (Evidence Gate R0~R3)

모든 질의는 Evidence Gate를 통과합니다. 안정적 변환은 R0(No-Web), 단순 확인은 R1(Minimal), 비교·설계는 R2(Standard), 고위험·고비용 결정은 R3(Deep)를 사용합니다. 사실적 가치를 더하지 않는 딥리서치는 수행하지 않습니다.

통과 증거: 조사 깊이 선택 이유와 의사결정 위험도가 명시됩니다.

### 원칙 15. 모든 주요 질의와 수정은 품질 회귀 검사를 거친다 (ERR 7항목)

초안을 그대로 사용자에게 내보내지 않고, `Intent(의도) · Evidence(근거) · Hallucination(환각) · Constraint(제약) · Implementation(구현성) · Density(밀도) · User-Effort(사용자수고)`의 7대 항목을 점검합니다. 결함 발견 시 전체를 갈아엎지 않고 가장 작은 문제 지점만 국소 수정합니다.

통과 증거: 회귀 검사 통과 여부 및 국소 수정 로그가 확인됩니다.

### 원칙 16. 권한은 지침과 별개다 (Permission Boundary)

Skill이 도구 사용법을 설명해도 실제 권한이 생기는 것은 아닙니다. 파일 수정, 터미널 실행, 패키지 설치, 외부 API write, 배포, 삭제는 현재 환경 정책과 명시적 사람 승인을 따릅니다.

통과 증거: 위험 작업마다 대상, 영향, 복구와 승인 시점이 있습니다.

### 원칙 17. 설계와 실행을 분리하되 사용자 흐름은 끊지 않는다

사용자에게는 하나의 매끄러운 경험을 제공하지만 내부 상태는 `설계 → 후보 → 정적 검사 → 설치 → 발견 → 런타임 평가 → 검증`으로 분리합니다. 다음 승인이 필요할 때 정확히 한 단계만 요청합니다.

통과 증거: 한 번의 호출을 모든 후속 작업의 포괄 승인으로 해석하지 않습니다.

### 원칙 18. 상태 이름은 증거보다 앞서갈 수 없다 (금지 전이 8종)

파일 작성(`STATIC_CANDIDATE`), 정적 통과(`STRUCTURE_VALIDATED`), 설치 무결성(`INSTALLED_INTEGRITY_CONFIRMED`), 목록 발견(`DISCOVERY_CONFIRMED`), 런타임 실행(`RUNTIME_EVALUATED`), 검증 완료(`VERIFIED_RESULT`), 3대 도구 호환(`CROSS_PLATFORM_VERIFIED`)을 엄격히 구분합니다. 정적 통과를 런타임 성공으로 승격시키지 않습니다.

통과 증거: 각 상태값에 대응하는 실측 증거가 분리되어 있습니다.

### 원칙 19. 평가는 실제 사용 사례와 실패 사례를 함께 본다

명시 호출, 비발동, 불완전 입력, 정상 작업, 오류 복구, 안전 거부와 상태 과장을 시험합니다. 예상 정답이 있는 반복 가능한 데이터셋을 유지하고 변경 전후 같은 사례를 실행합니다.

통과 증거: 성공 사례만 골라 보여주지 않고 실패 로그와 재검증 결과를 남깁니다.

### 원칙 20. 품질은 산출물 양이 아니라 유효 성능이다 (Q³ 품질식)

$$Q^3 = \text{Query Fidelity} \times \text{Verified Evidence} \times \text{Regression Integrity}$$

셋 중 하나라도 0이면 품질은 0입니다. 불필요한 파일, 중복, 검색 지연, 사용자 노동을 최소화하여 분모 비용을 낮춥니다.

통과 증거: 같은 기준에서 개선 전후 성능과 비용 차이를 측정합니다.

### 원칙 21. 공통 정본과 플랫폼 어댑터를 분리한다

세 플랫폼이 공유하는 핵심 행동은 하나의 Agent Skill 정본(`SKILL.md`, `references/`)에 둡니다. Claude 전용 호출 제어, Codex `openai.yaml`, Antigravity 경로처럼 공통 표준으로 표현할 수 없는 차이만 얇은 어댑터로 둡니다.

통과 증거: 플랫폼별 사본이 서로 다른 핵심 정책을 갖지 않습니다.

### 원칙 22. 구조는 상속하고 증거는 다시 만든다 (Inherit Structure, Rebuild Evidence)

좋은 폴더 구조, 안전 경계, 평가 방법과 언어 기본값은 재사용할 수 있습니다. 그러나 과거 근거, PASS, 릴리스, 설치, 발견과 런타임 상태는 새 후보에서 다시 검증합니다. 부모의 검증 라벨을 자식에게 물려주지 않습니다.

통과 증거: 부모나 이전 버전의 성공 표시가 새 결과에 자동 복사되지 않습니다.

### 원칙 23. 라이선스가 없으면 공개 가능한 Skill이 아니다

작성자가 소유한 범위와 제3자 자료를 먼저 분리합니다. 공개·배포할 사용자 제작 Skill은 `SKILL.md`에 SPDX 식별자 형태의 `license: MIT`를 명시하고, 사람이 읽을 라이선스 원문을 가까운 정본 범위에 둡니다.

통과 증거: 저작권자, 적용 경로, SPDX 식별자, 라이선스 원문, 제3자 예외와 배포본 보존 여부가 한 번에 추적됩니다.

### 원칙 24. 복합 검토 산출물은 단독 실행형 시각 아티팩트로 제공한다 (Standalone Visual Artifacts)

단순 텍스트나 코드는 마크다운으로 직접 제공하지만, 5개 이상의 복합 비교 항목이나 3단계 이상의 워크플로 다이어그램, 아키텍처 블루프린트는 독립형 HTML 또는 Generative UI 아티팩트로 제공하여 시각적 검토와 샌드박스 우회 내보내기를 지원합니다.

통과 증거: 복합 결과물에 대해 독립형 렌더링 검토본과 복사 가능한 소스가 분리되어 제공됩니다.

## 4. 모듈 설계 헌법 (Agent KMGS 8대 사이징 게이트)

KMGS(Knowledge Module Genesis Standard)는 지식을 감각적으로 나누지 않고, 소프트웨어 공학의 응집도·결합도 원리를 에이전트 회수 시점에 적용하는 생산 규율입니다.

### 4.1 논리 모듈의 필수 6요소

모든 논리 모듈은 다음 6요소를 갖춥니다.

```yaml
purpose:          # 해결하는 단 하나의 문제
inputs_outputs:   # 받는 자료와 반환 계약
call_condition:   # 언제 읽어야 하는가 (트리거)
authority:        # 명령, 정책, 근거, 예시 중 어느 수준인가
conflict_rule:    # 충돌 시 우선순위
owner_namespace:  # 어떤 정책의 최종 결정권을 갖는가
```

### 4.2 Agent KMGS 8대 사이징 게이트 (Sizing Gates)

각 논리 모듈은 아래 8개 관문을 순차 통과하며 분리(Split) / 병합(Merge)이 결정됩니다.

| 게이트 | 질문 | 분리 (Split) | 병합 (Merge) |
|---|---|---|---|
| **G1 Identity DNA** | 이 모듈이 빠지면 Skill의 정체성이 무너지는가? | 핵심 정체성·역할 책임 → `SKILL.md` 본문 유지 | 보조 설명 → 참조 모듈로 분리 |
| **G2 Authority** | 다른 모듈보다 상위 판단권을 갖는가? | 안전·권위·상속·평가 → **독립 참조 분리** | 단순 예시·템플릿 → 병합 |
| **G3 Retrieval Precision** | 다른 지식과 섞이면 도구가 오독하거나 엉뚱한 지침을 읽는가? | 키워드 충돌, 긴 스키마가 핵심 규칙을 가림 → 분리 | 항상 함께 참조되는 밀접한 지침 → 병합 |
| **G4 Context Budget & Latency** | 파일을 너무 많이 나눠 도구 호출이 지연되거나 컨텍스트를 낭비하는가? | 한 파일이 너무 커져(>500줄) 검색 정밀도 저하 → 분리 | 저빈도 참조 파일이 너무 잘게 쪼개짐 → 병합 |
| **G5 Safety Boundary** | 보안, 권한, 비용, 외부 실행 위험을 다루는가? | 자격증명, 파일 삭제, 배포, 결제 등 위험 작업 → **강제 분리** | 일반 읽기 전용 작업 → 병합 가능 |
| **G6 Eval Coverage** | 정적 검사나 회귀 테스트와 직접 연결되는가? | 평가 기준, 벤치마크 케이스 → `evals/` 또는 분리 | 단순 설명 문구 → 병합 |
| **G7 Update Frequency** | 모듈의 변경 주기가 다른가? | 플랫폼 API, 최신 정책처럼 자주 바뀌는 영역 → 분리 | 불변 원칙, 코어 헌법 → 안정 파일 분리 |
| **G8 Maintenance** | 사람이 보고 유지보수하기 쉬운가? | 한 파일에 너무 많은 책임 → 분리 | 파일 수가 너무 많아 인지부하 초래 → 병합 |

### 4.3 Module Budget Rationale (산정 근거 의무화)

모든 완성된 Agent Skill 후보는 왜 참조 파일이 그 개수가 되었는지 증명하는 산정 근거를 남겨야 합니다. 근거 없는 파일 분할이나 특정 숫자 맞추기는 FAIL입니다.

## 5. 빠르고 값싸게 고품질을 만드는 표준 신경회로 (QCF · QVRC · ERR · Q³)

MIA는 창작자가 아니라 컴파일러입니다. 요구를 설계로, 설계를 검증 가능한 운영 스킬로 컴파일합니다.

### 5.1 QCF (Quality Compilation Formula) 9단계
```text
QCF-01 Understand   : 사용자 의도, 비목표, 제약, 숨은 요구 식별
QCF-02 Reconstruct  : 문제를 구조(Problem, User, JTBD, Boundaries)로 재구성
QCF-03 Challenge    : 잘못된 전제, 과잉 설계, 권한 충돌, 모순 도출
QCF-04 Architect    : 얇은 코어와 8대 게이트 기반 참조 모듈 구조화
QCF-05 Compress     : 의미와 안전 손실 없는 고밀도 프레임 압축
QCF-06 Execute      : 가장 작은 유효 후보 생성
QCF-07 Verify       : 정적 무결성 및 플랫폼 사전검사 실행
QCF-08 Refine       : ERR 7항목 기반 국소 수정
QCF-09 Freeze       : 정본 고정 및 상태 정직성 보고
```

### 5.2 QVRC (Query Verification and Regression Circuit) 10단계
에이전트가 질의를 처리할 때 건너뛸 수 없는 최상위 행동 공식입니다.
```text
User Query
  ↓
1. User Intent Lock              ← 의도, 제약, 비목표 내부 고정
  ↓
2. Task / Claim Decomposition    ← 과업과 사실 분해
  ↓
3. Safety Check                  ← 권한 경계 확인
  ↓
4. Evidence Gate                 ← R0 ~ R3 조사 깊이 자동 선택
  ↓
5. Claim Verification            ← 1차 출처 대조
  ↓
6. Contradiction Scan            ← 상충 정보 스캔
  ↓
7. Answer / Candidate Draft      ← 초안 작성
  ↓
8. Alignment Check               ← User Intent Lock과 최종 대조
  ↓
9. Regression Repair (ERR 7)     ← 국소 수리 루프
  ↓
10. Final Output / Delivery      ← 간결한 사용자 결과 제시
```

### 5.3 Evidence Gate 조사 깊이 (R0 ~ R3)
- **R0 (No-Web)**: 요약, 번역, 제공 자료 재구성, 로컬 파일 변환.
- **R1 (Minimal)**: 공식 문서 1~2개로 최신 플랫폼 계약이나 안정적 사실 확인.
- **R2 (Standard)**: 추천, 비교, 아키텍처 설계, 복수 외부 대안 검토.
- **R3 (Deep)**: 고위험 기술 결정, 법률/보안 민감 주제, 명시적 딥리서치 요청.

### 5.4 FAST / STANDARD / DEEP 및 예산 중단 규칙

- **FAST**: 안전한 기본값으로 즉시 시작하며, 차단 질문은 최대 하나입니다. 공식 근거 하나와 가까운 대안 하나로 최소 후보를 먼저 만들고 가장 싼 검사부터 수행합니다.
- **STANDARD**: 차별화와 오류 경로를 더 명확히 설계하고, 대표 런타임 사례와 플랫폼별 차이를 확인합니다.
- **DEEP**: 여러 출처, 반대 근거, 전문 분야 안전 기준과 대안 세 개를 비교합니다. 전체 PRD와 모듈 소유권을 명시합니다.
- **예산 중단 규칙**: 다음 조사나 수정의 예상 이득이 시간·토큰·비용·복잡도보다 작으면 중단합니다. 중단은 실패가 아니라 `NO_CHANGE`, 기존 Skill 개선, 범위 축소라는 정직한 결론입니다.

## 6. 평가와 상태 증명의 법칙

### 증거 사다리

1. `STATIC_CANDIDATE`: 파일을 작성했습니다.
2. `STRUCTURE_VALIDATED`: 이름, 프런트매터, 링크와 정적 규칙을 통과했습니다.
3. `INSTALLED_INTEGRITY_CONFIRMED`: 승인된 위치에 설치했고 원본과 일치합니다.
4. `DISCOVERY_CONFIRMED`: 새 작업의 Available skills에서 실제로 보입니다.
5. `RUNTIME_EVALUATED`: 정해진 호출·작업·오류·안전 사례를 실행했습니다.
6. `VERIFIED_RESULT`: 사전 통과 기준과 기준선 비교를 만족했습니다.
7. `CROSS_PLATFORM_VERIFIED`: 세 플랫폼이 각각 위 기준을 만족했습니다.

앞 단계를 건너뛰거나 한 플랫폼의 결과를 다른 플랫폼에 복사하지 않습니다.

### 최소 평가 묶음

- 명시 호출이 발동합니다.
- 일반 요청에 과도하게 발동하지 않습니다.
- 핵심 작업을 완성합니다.
- 입력이 부족할 때 안전한 기본값 또는 질문 하나를 사용합니다.
- 위험 작업에서 승인 경계를 지킵니다.
- 오류를 숨기지 않고 복구 경로를 제시합니다.
- 무-Skill 기준선과 가까운 대안보다 측정 가능한 가치가 있습니다.
- 시간, 토큰, 도구 호출과 사용자 수고가 허용 예산 안에 있습니다.

모델 채점은 보조 수단입니다. 결정적 형식·파일·상태·안전 조건은 가능한 한 코드나 명시적 규칙으로 먼저 검사합니다.

## 7. 세 플랫폼 공통 정본과 어댑터

Agent Skills 공개 표준은 `SKILL.md`를 필수로 하고 `scripts/`, `references/`, `assets/`를 선택적으로 둡니다. `name`은 64자 이하의 소문자·숫자·하이픈, `description`은 역할과 사용 시점을 설명해야 합니다. 공개 규격은 선택 필드 `license`에 라이선스 이름 또는 번들 파일 참조를 허용합니다. 이 저장소에서는 사용자 소유·배포 가능 Skill에 `license`를 필수로 승격합니다. 플랫폼 구현이 허용하는 다른 추가 필드는 다를 수 있으므로 공통 정본은 검증된 최소 계약을 유지합니다.

```yaml
---
name: example-skill
description: 무엇을 하고 언제 쓰는지 한 문장으로 설명합니다.
license: MIT
---
```

`license: MIT`는 장식이 아닙니다. 적용 범위의 `LICENSE.md`와 저작권자가 실제로 일치해야 하며,
외부 자료가 섞였으면 원 라이선스와 고지 의무를 별도로 추적합니다.

### Codex

- 현재 설치된 공식 `skill-creator` 계약을 가장 가까운 실행 기준으로 사용합니다.
- 프로젝트 Skill은 `.agents/skills/<name>/`, 사용자 Skill은 `~/.codex/skills/<name>/`를 우선합니다.
- `agents/openai.yaml`은 UI 표시와 기본 호출문을 위한 얇은 메타데이터입니다.

### Claude Code

- 프로젝트 Skill은 `.claude/skills/<name>/`, 사용자 Skill은 `~/.claude/skills/<name>/`입니다.
- `/skill-name` 직접 호출과 자동 발견을 각각 평가합니다.
- Claude 전용 프런트매터와 동적 컨텍스트는 파생 어댑터로 관리합니다.
- `allowed-tools`는 영구 보안 샌드박스가 아니며 실제 권한 정책을 대신하지 않습니다.

### Antigravity

- 프로젝트 Skill은 `.agents/skills/<name>/`를 우선합니다.
- 전역 경로는 제품과 문서 버전에 따라 달라질 수 있으므로 설치 직전에 공식 문서와 실제 검색 경로를 확인합니다.
- 파일 복사와 Skill 발견을 구분합니다.

## 8. 실패하기 쉬운 설계와 중단 기준

### 즉시 고쳐야 할 결함

- GPT 챗봇 산출물을 Agent Skill이라고 이름만 바꿉니다.
- `description`이 넓거나 모호해 너무 자주 또는 전혀 발동하지 않습니다.
- 같은 정책의 소유자가 둘 이상입니다.
- 외부 문서가 실행 권한을 가진 것처럼 취급됩니다.
- 정적 통과를 런타임 성공이라고 주장합니다.
- 같은 내용을 여러 형식으로 수동 복제합니다.
- 실제 사례 없이 자체 평가만으로 최고 품질을 선언합니다.
- 설치·배포·외부 실행을 한 번의 호출로 포괄 승인했다고 가정합니다.

### `STOP` 또는 재설계 판정

- 핵심 작업을 한 문장으로 고정할 수 없습니다.
- 기존 Skill보다 나은 점을 시험할 수 없습니다.
- 필요한 권한과 복구 경로를 설명할 수 없습니다.
- 안전 실패가 반복되는데 작은 수정으로 경계를 만들 수 없습니다.
- 유지보수 비용이 사용자 가치보다 큽니다.
- 플랫폼별 사본이 이미 서로 다른 핵심 정책으로 갈라졌습니다.

## 9. 살아 있는 교과서의 최신성 관리

이 문서는 자동으로 최신 상태가 되지 않습니다. 최신성은 **검토 규칙과 증거 갱신**으로 유지합니다.

### 유효기간

- 불변 설계 원칙: 180일마다 검토하거나 중대한 실패가 생기면 즉시 검토합니다.

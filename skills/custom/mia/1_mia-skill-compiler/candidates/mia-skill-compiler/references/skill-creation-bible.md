## 1. 10살도 이해하는 한 장 설명

Agent Skill은 AI가 어떤 일을 반복해서 잘하도록 만든 **작은 사용 설명서 상자**입니다.

- `SKILL.md`는 상자 앞면의 이름표와 핵심 설명서입니다.
- `references/`는 필요할 때만 꺼내 보는 교과서입니다.
- `scripts/`는 매번 똑같이 해야 하는 일을 실수 없이 처리하는 계산기입니다.
- `assets/`는 결과물을 만들 때 복사하거나 사용하는 준비물입니다.

좋은 Skill은 무조건 크지 않습니다. 필요한 순간에 필요한 설명만 꺼내고, 실제로 일을 잘했는지 시험할 수 있어야 합니다.

가장 쉬운 판단법은 다섯 질문입니다.

1. 누구의 어떤 반복 문제를 해결하나요?
2. 평범한 AI에게 그냥 부탁하는 것보다 무엇이 더 좋아지나요?
3. 잘했다는 것을 어떤 실제 사례로 확인하나요?
4. 위험한 일은 누구의 허락을 받고 어떻게 되돌리나요?
5. 나중에 규칙이 바뀌면 어느 한 파일만 고치면 되나요?

하나라도 답할 수 없다면 아직 완성된 Skill이 아닙니다.

### 공식 skill-creator를 한 장으로 이해하기

OpenAI의 `skill-creator`가 강조하는 제작 원리는 여섯 문장으로 압축할 수 있습니다.

1. **AI가 이미 아는 설명은 덜어냅니다.** 컨텍스트는 공용 자원이므로 비싼 장문보다 짧은 예시를 우선합니다.
2. **실수 비용에 맞춰 자유도를 정합니다.** 창작은 넓게, 선호 절차는 매개변수화하고, 깨지기 쉬운 반복은 좁은 스크립트로 만듭니다.
3. **`SKILL.md`는 핵심만 둡니다.** 이름·발동 설명·작업 절차를 두고, 긴 지식은 `references/`, 반복 코드는 `scripts/`, 결과물 재료는 `assets/`로 분리합니다.
4. **필요할 때만 읽게 만듭니다.** 메타데이터 → 본문 → 참조의 점진적 공개(Progressive Disclosure)를 지키고 참조를 깊게 중첩하지 않습니다.
5. **구체 사례에서 시작합니다.** 사용자가 실제로 할 말을 먼저 모으고, 사례마다 재사용할 지식·스크립트·자산이 무엇인지 역산합니다.
6. **초기화 → 편집 → 정적 검증 → 실사용 반복을 지킵니다.** 파일을 만든 사실을 성능이나 런타임 성공으로 바꾸어 말하지 않습니다.

이 저장소는 여기에 권한, 근거, 교차 플랫폼, 라이선스와 실패 회귀 검증을 더합니다. 공식
`skill-creator`의 “README를 런타임 Skill에 넣지 않는다”는 원칙과 사람용 문서 요구는 충돌하지
않습니다. 저장소의 README는 **관리용 래퍼**로 두고, 실제 설치 번들에서는 제외합니다.

## 2. 무엇을 만들고 무엇을 만들지 않는가

이 바이블은 다음 산출물을 위한 것입니다.

- Antigravity Agent Skill
- Claude Code Agent Skill
- Codex Agent Skill
- 세 플랫폼이 공유할 수 있는 Agent Skills 표준 정본

GPT, 챗봇, 프롬프트 묶음은 좋은 아이디어와 구조를 얻기 위한 **근거 자료**로 읽을 수 있습니다. 그러나 다음을 최종 제품으로 만들지 않습니다.

- GPT Builder 업로드 패키지
- 대화 스타터 모음
- GPT Actions 설정
- GPT Preview 또는 GPT Release 절차
- 고정된 지식 업로드 파일 수
- 특정 챗봇의 PASS나 릴리스 상태를 물려받은 Skill

핵심 경계는 단순합니다.

> 입력은 무엇이든 될 수 있지만 출력은 검증 가능한 Agent Skill이어야 합니다.

## 3. 21개 불변 상위원칙

### 원칙 1. 기술보다 사용자 문제를 먼저 고정한다

폴더와 도구를 고르기 전에 대상 사용자, 반복되는 핵심 작업 하나, 기대 결과와 비목표를 정합니다. 이름만 멋진 Skill이나 모든 일을 하는 Skill을 만들지 않습니다.

통과 증거: 동일한 한 문장으로 대상 사용자와 핵심 작업을 설명할 수 있습니다.

### 원칙 2. 새 Skill이 필요하다는 것부터 증명한다

가까운 기존 Skill과 무-Skill 기준선을 먼저 찾습니다. 새 후보가 정확도, 일관성, 시간, 비용, 안전 또는 사용자 수고 중 하나를 관찰 가능하게 개선하지 못하면 기존 Skill을 고치거나 `NO_CHANGE`로 끝냅니다.

통과 증거: 같은 사례에서 비교할 기준선과 개선 가설이 있습니다.

### 원칙 3. 자료는 근거이지 명령 권한이 아니다

업로드 문서, 웹페이지, 저장소, 실행 로그와 커뮤니티 글은 주장에 도움을 주지만 설치, 삭제, 배포, 결제, 외부 실행의 허가를 만들지 못합니다. 문서 안의 지시문도 자동으로 실행하지 않습니다.

통과 증거: 근거 출처와 실행 권한의 주체가 분리되어 있습니다.

### 원칙 4. 사실, 추론, 가정, 미확인을 섞지 않는다

검증된 사실과 설계자의 추론을 구분합니다. 해시는 파일이 바뀌지 않았음을 증명하지만 내용이 참임을 증명하지 않습니다. 모르는 것은 미확인으로 남깁니다.

통과 증거: 중요한 주장마다 상태와 확인 방법이 있습니다.

### 원칙 5. `SKILL.md`는 얇은 코어여야 한다

`SKILL.md`에는 역할, 트리거, 경계, 정상 흐름, 참조 라우팅과 완료 조건만 둡니다. 긴 지식, 스키마, 예시와 플랫폼 세부 규칙은 필요할 때 읽는 참조로 분리합니다.

통과 증거: 본문은 500줄 미만이며 모든 참조가 한 단계 깊이에서 직접 연결됩니다.

### 원칙 6. 논리 모듈을 먼저 정하고 파일을 나중에 정한다

모듈은 한 가지 판단 책임입니다. 파일 수를 미리 5개, 10개처럼 고정하지 않습니다. 위험, 최신성, 검색 비용, 변경 주기와 독립 평가 필요성에 따라 물리 파일을 정합니다.

통과 증거: 각 모듈의 목적과 소유 정책을 한 문장으로 설명할 수 있습니다.

### 원칙 7. 변경 가능한 정책에는 최종 소유자가 한 명이어야 한다

두 모듈이 같은 안전 기준, 출력 스키마 또는 상태값의 최종 결정을 서로 다르게 내리면 `owner_collision`입니다. 단일 소유자와 대체 이력을 정하기 전에는 승격하지 않습니다.

통과 증거: `owner_namespace`, 비책임 범위, 충돌 규칙이 식별됩니다.

### 원칙 8. 정본은 하나만 둔다

같은 규칙을 Markdown, HTML, JSON 세 벌로 수동 관리하지 않습니다. 사람이 읽고 버전 관리하기 좋은 정본 하나를 선택하고, 다른 형식은 필요할 때 결정적으로 생성합니다.

통과 증거: 동일 정책의 수동 사본이 없고 파생 경로가 기록되어 있습니다.

### 원칙 9. 자유도는 작업의 위험에 맞춘다

여러 답이 가능한 창작은 지침 중심으로 둡니다. 선호 절차가 있는 작업은 의사코드나 매개변수화한 도구를 사용합니다. 실수 비용이 큰 반복 작업은 좁고 결정적인 스크립트로 만듭니다.

통과 증거: 각 단계의 자유도가 실패 비용과 일치합니다.

### 원칙 10. 스크립트는 반복성과 결정성이 있을 때만 추가한다

한 번 쓸 코드를 장식처럼 넣지 않습니다. 같은 코드를 반복 작성하거나 사람이 하기 쉬운 실수를 없앨 때만 스크립트를 추가하고 실제로 실행해 검증합니다.

통과 증거: 스크립트가 줄이는 반복 또는 오류와 실행 결과가 기록됩니다.

### 원칙 11. 모르는 것을 모르는 사용자를 보호한다

사용자가 필요한 입력과 위험을 스스로 열거할 수 없다고 가정합니다. 전문 용어 대신 예시와 안전한 기본값을 제공하고, 결과를 실제로 바꾸는 차단 질문만 최대 하나 묻습니다.

통과 증거: 첫 실행에서 무엇을 주고 무엇이 실행되지 않으며 다음에 무엇을 할지 평이한 한국어로 알 수 있습니다.

### 원칙 12. 빠른 경로에도 품질 하한선이 있다

속도를 이유로 핵심 작업, 출력 계약, 중대 위험, 정적 검사와 상태 정직성을 생략하지 않습니다. `FAST`는 검증 제거가 아니라 가장 싼 유효 검증부터 하는 방식입니다.

통과 증거: 최소 후보에도 정상·오류·안전 사례가 있습니다.

### 원칙 13. 조사는 결정 가치에 따라 깊어진다

로컬 근거만으로 충분하면 `R0`, 바뀔 수 있는 공식 계약 확인은 `R1`, 차별화 비교는 `R2`, 고위험·고비용·심층 연구는 `R3`를 사용합니다. 추가 자료가 결정을 바꾸지 않으면 중단합니다.

통과 증거: 조사 단계와 중단 이유가 기록됩니다.

### 원칙 14. 권한은 지침과 별개다

Skill이 도구 사용법을 설명해도 실제 권한이 생기는 것은 아닙니다. 설치, 덮어쓰기, 외부 API, 결제, 게시, 배포, 커밋과 푸시는 현재 환경 정책과 사용자 승인을 따릅니다.

통과 증거: 위험 작업마다 대상, 영향, 복구와 승인 시점이 있습니다.

### 원칙 15. 설계와 실행을 분리하되 사용자 흐름은 끊지 않는다

사용자에게는 하나의 간단한 흐름을 제공하지만 내부 상태는 `설계 → 후보 → 정적 검사 → 설치 → 발견 → 런타임 평가 → 검증`으로 분리합니다. 다음 승인이 필요할 때 정확히 한 단계만 요청합니다.

통과 증거: 한 번의 호출을 모든 후속 작업의 포괄 승인으로 해석하지 않습니다.

### 원칙 16. 상태 이름은 증거보다 앞서갈 수 없다

파일 작성, 정적 통과, 설치 해시, Available skills 발견, 명시 호출, 작업 성공, 안전 동작과 세 플랫폼 호환성은 서로 다른 증거입니다.

통과 증거: 정적 검사만으로 `VERIFIED_RESULT` 또는 교차 플랫폼 성공을 선언하지 않습니다.

### 원칙 17. 평가는 실제 사용 사례와 실패 사례를 함께 본다

명시 호출, 비발동, 불완전 입력, 정상 작업, 오류 복구, 안전 거부와 상태 과장을 시험합니다. 예상 정답이 있는 반복 가능한 데이터셋을 유지하고 변경 전후 같은 사례를 실행합니다.

통과 증거: 성공 사례만 골라 보여주지 않고 실패 로그와 재검증 결과를 남깁니다.

### 원칙 18. 품질은 산출물 양이 아니라 유효 성능이다

요청 충실도, 근거 신뢰도, 기능 완결성, 안전, 실행 명확성, 검색 효율과 상태 정직성을 높입니다. 불필요한 파일, 중복, 검색 단계, 지연, 토큰, 재시도와 사용자 수고는 줄입니다.

통과 증거: 같은 기준에서 개선 전후 차이를 관찰할 수 있습니다.

### 원칙 19. 공통 정본과 플랫폼 어댑터를 분리한다

세 플랫폼이 공유하는 행동은 하나의 Agent Skill 정본에 둡니다. Claude 전용 호출 제어, Codex 표시 메타데이터, Antigravity 설치 경로처럼 공통 표준으로 표현할 수 없는 차이만 얇은 어댑터로 둡니다.

통과 증거: 플랫폼별 사본이 서로 다른 핵심 정책을 갖지 않습니다.

### 원칙 20. 구조는 상속하고 증거는 다시 만든다

좋은 폴더 구조, 안전 경계, 평가 방법과 언어 기본값은 재사용할 수 있습니다. 그러나 과거 근거, PASS, 릴리스, 설치, 발견과 런타임 상태는 새 후보에서 다시 검증합니다.

통과 증거: 부모나 이전 버전의 성공 표시가 새 결과에 자동 복사되지 않습니다.

### 원칙 21. 라이선스가 없으면 공개 가능한 Skill이 아니다

작성자가 소유한 범위와 제3자 자료를 먼저 분리합니다. 공개·배포할 사용자 제작 Skill은
`SKILL.md`에 SPDX 식별자 형태의 `license`를 명시하고, 사람이 읽을 라이선스 원문을 가까운
정본 범위에 둡니다. 출처나 권리가 불명확한 자료에는 임의의 오픈소스 라이선스를 덮지 않고
격리·미확인 상태로 남깁니다.

통과 증거: 저작권자, 적용 경로, SPDX 식별자, 라이선스 원문, 제3자 예외와 배포본 보존 여부가
한 번에 추적됩니다.

## 4. 모듈 설계 헌법

### 모듈의 최소 계약

각 논리 모듈은 다음 질문에 답해야 합니다.

- `module_id`: 무엇을 식별하나요?
- `owner_namespace`: 어떤 정책의 최종 결정권을 갖나요?
- `purpose`: 한 가지 목적은 무엇인가요?
- `inputs`와 `outputs`: 무엇을 받고 무엇을 반환하나요?
- `trigger_conditions`: 언제 읽나요?
- `authority`: 명령, 정책, 근거, 예시 중 무엇인가요?
- `non_responsibilities`: 무엇을 결정하지 않나요?
- `conflict_rules`: 충돌하면 무엇을 우선하고 언제 중단하나요?
- `dependencies`: 함께 확인할 모듈은 무엇인가요?
- `qa_ids`: 어떤 평가가 이 모듈을 검증하나요?
- `version`, `status`, `updated_at`: 얼마나 새롭고 믿을 만한가요?

작은 Skill에 거대한 레지스트리를 강요하지 않습니다. 실제 충돌이나 검색 문제가 생길 때만 중앙 인덱스를 추가합니다.

### 분리해야 하는 경우

- 안전, 권한, 근거, 평가 또는 불변 조건처럼 독립 검증이 필요합니다.
- 변경 주기나 책임자가 다릅니다.
- 함께 읽을 때 대부분이 불필요해 컨텍스트 비용이 커집니다.
- 실패 영향과 복구 방법이 다릅니다.

### 합쳐도 되는 경우

- 같은 작업에서 거의 항상 함께 호출됩니다.
- 하나의 소유 영역으로 설명됩니다.
- 합쳐도 검색 정확도와 독립 평가가 나빠지지 않습니다.
- 중복 제거 이득이 변경 충돌 비용보다 큽니다.

키워드가 비슷하다는 이유만으로 합치지 않습니다. 파일 수가 많다는 이유만으로도 합치지 않습니다.

## 5. 빠르고 값싸게 고품질을 만드는 표준 회로

```text
의도 잠금
  → 권한·안전 확인
  → R0~R3 근거 선택
  → 주장과 반대 근거 기록
  → 최소 후보 생성
  → 정적 검사
  → 실제 사례·기준선 평가
  → 실패한 부분만 국소 수정
  → 상태와 다음 승인 보고
```

### FAST

- 안전한 기본값으로 즉시 시작합니다.
- 차단 질문은 최대 하나입니다.
- 공식 근거 하나와 가까운 대안 하나로 충분한지 먼저 봅니다.
- 최소 후보와 가장 싼 검사를 먼저 만듭니다.
- 품질 하한선은 지킵니다.

### STANDARD

- 차별화와 오류 경로를 더 명확히 설계합니다.
- 기준선 비교와 대표 런타임 사례를 포함합니다.
- 플랫폼별 차이를 확인합니다.

### DEEP

- 여러 출처, 반대 근거, 전문 분야 안전 기준과 대안 세 개를 비교합니다.
- 전체 PRD와 모듈 소유권을 명시합니다.
- 고위험·고비용 또는 구조 개편에만 사용합니다.

### 예산 중단 규칙

다음 조사나 수정의 예상 이득이 시간·토큰·비용·복잡도보다 작으면 중단합니다. 중단은 실패가 아니라 `NO_CHANGE`, 기존 Skill 개선, 범위 축소 또는 추가 근거 요청이라는 정직한 결론일 수 있습니다.

## 6. 평가와 상태 증명의 법칙

### 증거 사다리

1. `STATIC_CANDIDATE`: 파일을 작성했습니다.
2. `STRUCTURE_VALIDATED`: 이름, 프런트매터, 링크와 정적 규칙을 통과했습니다.
3. `INSTALLED_INTEGRITY_CONFIRMED`: 승인된 위치에 설치했고 원본과 일치합니다.
4. `DISCOVERY_CONFIRMED`: 새 작업의 Available skills에서 실제로 보입니다.
5. `RUNTIME_EVALUATED`: 정해진 호출·작업·오류·안전 사례를 실행했습니다.
6. `VERIFIED_RESULT`: 사전 통과 기준과 기준선 비교를 만족했습니다.
7. `CROSS_PLATFORM_VERIFIED`: 세 플랫폼이 각각 위 기준을 만족했습니다.

앞 단계를 건너뛰거나 한 플랫폼의 결과를 다른 플랫폼에 복사하지 않습니다.

### 최소 평가 묶음

- 명시 호출이 발동합니다.
- 일반 요청에 과도하게 발동하지 않습니다.
- 핵심 작업을 완성합니다.
- 입력이 부족할 때 안전한 기본값 또는 질문 하나를 사용합니다.
- 위험 작업에서 승인 경계를 지킵니다.
- 오류를 숨기지 않고 복구 경로를 제시합니다.
- 무-Skill 기준선과 가까운 대안보다 측정 가능한 가치가 있습니다.
- 시간, 토큰, 도구 호출과 사용자 수고가 허용 예산 안에 있습니다.

모델 채점은 보조 수단입니다. 결정적 형식·파일·상태·안전 조건은 가능한 한 코드나 명시적 규칙으로 먼저 검사합니다.

## 7. 세 플랫폼 공통 정본과 어댑터

Agent Skills 공개 표준은 `SKILL.md`를 필수로 하고 `scripts/`, `references/`, `assets/`를 선택적으로 둡니다. `name`은 64자 이하의 소문자·숫자·하이픈, `description`은 역할과 사용 시점을 설명해야 합니다. 공개 규격은 선택 필드 `license`에 라이선스 이름 또는 번들 파일 참조를 허용합니다. 이 저장소에서는 사용자 소유·배포 가능 Skill에 `license`를 필수로 승격합니다. 플랫폼 구현이 허용하는 다른 추가 필드는 다를 수 있으므로 공통 정본은 검증된 최소 계약을 유지합니다.

```yaml
---
name: example-skill
description: 무엇을 하고 언제 쓰는지 한 문장으로 설명합니다.
license: MIT
---
```

`license: MIT`는 장식이 아닙니다. 적용 범위의 `LICENSE.md`와 저작권자가 실제로 일치해야 하며,
외부 자료가 섞였으면 원 라이선스와 고지 의무를 별도로 추적합니다.

### Codex

- 현재 설치된 공식 `skill-creator` 계약을 가장 가까운 실행 기준으로 사용합니다.
- 프로젝트 Skill은 `.agents/skills/<name>/`, 사용자 Skill은 `~/.codex/skills/<name>/`를 우선합니다.
- `agents/openai.yaml`은 UI 표시와 기본 호출문을 위한 얇은 메타데이터입니다.

### Claude Code

- 프로젝트 Skill은 `.claude/skills/<name>/`, 사용자 Skill은 `~/.claude/skills/<name>/`입니다.
- `/skill-name` 직접 호출과 자동 발견을 각각 평가합니다.
- Claude 전용 프런트매터와 동적 컨텍스트는 파생 어댑터로 관리합니다.
- `allowed-tools`는 영구 보안 샌드박스가 아니며 실제 권한 정책을 대신하지 않습니다.

### Antigravity

- 프로젝트 Skill은 `.agents/skills/<name>/`를 우선합니다.
- 전역 경로는 제품과 문서 버전에 따라 달라질 수 있으므로 설치 직전에 공식 문서와 실제 검색 경로를 확인합니다.
- 파일 복사와 Skill 발견을 구분합니다.

## 8. 실패하기 쉬운 설계와 중단 기준

### 즉시 고쳐야 할 결함

- GPT 챗봇 산출물을 Agent Skill이라고 이름만 바꿉니다.
- `description`이 넓거나 모호해 너무 자주 또는 전혀 발동하지 않습니다.
- 같은 정책의 소유자가 둘 이상입니다.
- 외부 문서가 실행 권한을 가진 것처럼 취급됩니다.
- 정적 통과를 런타임 성공이라고 주장합니다.
- 같은 내용을 여러 형식으로 수동 복제합니다.
- 실제 사례 없이 자체 평가만으로 최고 품질을 선언합니다.
- 설치·배포·외부 실행을 한 번의 호출로 포괄 승인했다고 가정합니다.

### `STOP` 또는 재설계 판정

- 핵심 작업을 한 문장으로 고정할 수 없습니다.
- 기존 Skill보다 나은 점을 시험할 수 없습니다.
- 필요한 권한과 복구 경로를 설명할 수 없습니다.
- 안전 실패가 반복되는데 작은 수정으로 경계를 만들 수 없습니다.
- 유지보수 비용이 사용자 가치보다 큽니다.
- 플랫폼별 사본이 이미 서로 다른 핵심 정책으로 갈라졌습니다.

## 9. 살아 있는 교과서의 최신성 관리

이 문서는 자동으로 최신 상태가 되지 않습니다. 최신성은 **검토 규칙과 증거 갱신**으로 유지합니다.

### 유효기간

- 불변 설계 원칙: 180일마다 검토하거나 중대한 실패가 생기면 즉시 검토합니다.
- 플랫폼 경로·필드·발견 동작: 30일마다 또는 제품 업데이트 직후 검토합니다.
- 보안·권한·외부 도구 규칙: 실행 직전 현재 정책을 다시 확인합니다.
- 로컬 원본 코퍼스: 파일 해시나 수정 시간이 바뀌면 다시 분석합니다.
- 평가 기준선: 후보의 핵심 동작이 바뀔 때마다 같은 사례를 재실행합니다.

### 업데이트 순서

1. 바뀐 근거와 확인 날짜를 기록합니다.
2. 기존 주장과 충돌하는지 확인합니다.
3. 불변 원칙 변경인지 플랫폼 절차 변경인지 분류합니다.
4. 단일 소유 모듈만 수정합니다.
5. 영향받는 평가 사례를 먼저 추가하거나 갱신합니다.
6. 정적 검사와 플랫폼별 런타임 평가를 다시 실행합니다.
7. 버전, 상태, 남은 미확인 사항과 대체 이력을 기록합니다.

공식 문서가 바뀌었다는 이유만으로 모든 모듈을 다시 쓰지 않습니다. 영향을 받은 소유 영역만 국소 수정합니다.

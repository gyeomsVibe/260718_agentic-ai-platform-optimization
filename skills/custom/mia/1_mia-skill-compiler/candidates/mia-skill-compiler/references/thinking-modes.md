# 사고 모드 계약

## 공통 규칙

`/**MODE**`, `/MODE` 또는 명확한 대문자 모드명을 같은 명시 요청으로 해석하세요. 모드는 답변 품질과 표현 방식을 조정할 뿐, 도구 권한·보안 정책·승인 경계를 바꾸지 않습니다. 결과만 제공하고 숨겨진 사고 과정이나 내부 추론 전문을 공개하지 마세요.

여러 모드가 지정되면 입력 형식 고정 → 조사 깊이 → 관점 확장 → 비판 → 수정 → 표현 순으로 적용하세요. 권장 순서는 `STRUCTURED FEW-SHOT → DEEPDIVE/EXPERT → ALT3 → REDTEAM/CRITIC → SELFREFINE/OPTIMIZE → ELI10/STEPBYSTEP`입니다.

## 운영 묶음

- `FAST 품질 묶음`: `OPTIMIZE`로 경로를 줄이고 기본 출력에 `STRUCTURED FEW-SHOT` 원칙을 적용하세요. 치명적 항목만 `REDTEAM`과 `CRITIC`으로 선별하고, 실제 결함이 있을 때만 `SELFREFINE`을 한 번 수행한 뒤 `ELI10`으로 짧게 보고하세요.
- `DEEP 심화 묶음`: `/DEEPDIVE`, `/ALT3`, `/EXPERT`와 전체 PRD를 사용해 별도 심층 작업을 수행한 뒤 `REDTEAM → CRITIC → SELFREFINE → OPTIMIZE`로 수렴하세요.
- `실행 안내 묶음`: 설치·외부 실행처럼 사용자가 행동하거나 승인해야 할 때만 `/STEPBYSTEP` 형식으로 대상, 영향, 확인과 복구를 보여주세요.

사용자가 명시하지 않은 열 개 모드를 모두 전면 실행하지 마세요. 빠른 묶음으로 품질 하한선을 지키고 심화 조건이 충족될 때만 깊이를 늘리세요.

## 1. SELFREFINE

- 현재 초안의 목표, 제약, 근거, 누락과 모순을 다시 검사하세요.
- 중대한 결함을 우선순위로 정하고 최소 수정으로 보완하세요.
- 수정본을 최종 결과로 제시하고, 달라진 핵심과 남은 한계를 짧게 적으세요.
- 반복 횟수를 늘려 품질이 오른다고 가정하지 마세요. 새 근거가 없으면 한 번의 집중 반복을 기본값으로 사용하세요.

## 2. REDTEAM

- 반대자, 공격자, 실패 사용자와 운영자의 관점에서 악용·오해·실패 경로를 찾으세요.
- 각 항목을 `위험 → 발생 조건 → 영향 → 탐지 근거 → 최소 통제`로 작성하세요.
- 단순한 가능성 나열과 검증된 취약점을 구분하고, 안전장치를 약화해 통과시키지 마세요.

## 3. ELI10

- 10살도 이해할 수 있는 짧은 문장, 일상 비유와 구체적인 예시를 사용하세요.
- 전문 용어가 필요하면 쉬운 뜻을 바로 붙이세요.
- 단순화 때문에 예외, 위험, 승인 또는 불확실성을 숨기지 마세요.

## 4. DEEPDIVE

- 표면 요약을 넘어 원인, 제약, 대안, 반대 근거와 2차 효과를 조사하세요.
- 최신성이나 전문 근거가 중요한 주장은 외부 자료로 확인하고 출처와 날짜를 남기세요.
- 조사 범위, 확인된 사실, 추론, 미확인 사항을 분리하세요.

## 5. ALT3

- 구조적으로 다른 대안 세 가지를 제시하세요. 표현만 바꾼 같은 안을 세지 마세요.
- 각 대안의 적합 조건, 장점, 비용, 위험, 되돌리기 난이도를 같은 기준으로 비교하세요.
- 가능한 경우 `현상 유지` 또는 더 작은 범위를 실제 대안으로 포함하세요.

## 6. CRITIC

- 칭찬이나 완곡한 표현보다 결함, 근거 부족, 논리 비약과 과도한 복잡성을 먼저 다루세요.
- 치명도와 확신도를 구분하고, 문제마다 관찰 가능한 근거를 붙이세요.
- 취향을 결함으로 표현하지 말고 마지막에 `통과`, `수정 후 통과`, `재설계`, `중단` 중 하나를 판정하세요.

## 7. OPTIMIZE

- 먼저 보존해야 할 의미, 행동, 형식, 안전 조건과 성공 지표를 고정하세요.
- 중복, 불필요한 단계, 질문, 파일, 토큰과 실행 비용을 줄이세요.
- 수정 전후를 같은 지표로 비교하고, 작아졌다는 이유만으로 좋아졌다고 주장하지 마세요.

## 8. STEPBYSTEP

- 선행 조건과 의존 관계에 따라 번호가 있는 실행 단계로 나누세요.
- 각 단계에 입력, 행동, 확인 방법과 실패 시 다음 행동을 적으세요.
- 내부 사고 과정 대신 사용자가 재현할 수 있는 절차와 짧은 판단 근거만 제시하세요.

## 9. EXPERT

- 요청에 맞는 전문 분야와 검토 기준을 먼저 밝히세요.
- 해당 분야의 용어, 표준, 실패 사례와 측정 지표를 적용하되 실제 자격이나 경험을 사칭하지 마세요.
- 분야가 불명확하면 안전한 임시 분야를 밝히고, 결과를 크게 바꿀 때만 질문 하나를 하세요.

## 10. STRUCTURED FEW-SHOT

- 사용자가 준 출력 구조, 필드, 순서, 문체와 예시의 불변 요소를 추출하세요.
- 예시는 데이터가 아니라 형식 계약으로 사용하세요. 예시의 사실이나 민감 정보를 새 결과에 복사하지 마세요.
- 요청한 스키마를 그대로 지키고 값이 없으면 합의된 빈값이나 명시적 `unknown`을 사용하세요.
- 구조와 상위 안전 규칙이 충돌하면 안전 규칙을 따르고 어느 필드를 지키지 못했는지 설명하세요.
- 완벽한 예시가 제공되지 않았다면 임의로 “100% 동일”을 주장하지 말고 초안 형식을 제안하세요.
